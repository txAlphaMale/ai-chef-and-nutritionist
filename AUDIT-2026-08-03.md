# Chef — Architecture Review and Code Audit

Date: 2026-08-03
Scope: full read of `backend/` (16.4k LOC Python), `frontend/src` (11.5k LOC React/CSS), Docker/CI/packaging, and PROJECT-PLAN.md.
Method: read the code, then verified every external claim against primary sources (Ollama docs, ollama-python, WebKit/W3C media-capture behaviour). Nothing below is inferred from the plan file's own narrative.

---

## 1. Architectural model

### What the app is supposed to be

A single-household, self-hosted meal-planning system that closes a loop:

```
  inventory (what we have)  ──┐
  household profile / DRI ────┼──> weekly meal plan ──> grocery list
  health metrics / trends  ───┤          │
  knowledge corpus (RAG)   ───┘          ├──> recipes (catalog + AI-authored)
                                          └──> confirm cooked ──> deduct inventory ──┐
                                                                                      └──> back to inventory
```

Everything else — dining out, calendars, barcode/receipt intake, cost, recall alerts, cook mode — hangs off that spine.

### Runtime shape

| Layer | Reality |
|---|---|
| Host | WSL2 Debian on Windows, Intel 6700K, 2× GTX 1080 Ti (11 GB each, not pooled) |
| Inference | Ollama on the host, reached over the network. Chat model `qwen3.6:27b` — a *thinking-capable* model, and at 27B a tight fit on 11 GB |
| Containers | `backend` (FastAPI, SQLite, single process) and `frontend` (Node static server + reverse proxy). Frontend is the only origin a browser touches |
| Persistence | One SQLite file + image/knowledge dirs on a named volume |
| Concurrency | FastAPI event loop + threadpool for `def` routes + **exactly one** background worker thread for all AI work |

### The three architectural properties that actually govern correctness

These are the constraints everything else has to respect. Most of the defects below are a failure to respect one of them.

1. **Every AI response is untrusted input.** The model is small, local, quantised, and thinking-capable. Any design that requires the model to voluntarily emit clean JSON is a design that fails intermittently forever.
2. **There is exactly one GPU budget and one worker thread.** Anything that can block that thread indefinitely takes down *every* AI feature in the app, not just its own.
3. **Ingredient identity is the app's join key, and it is free text.** Inventory rows, recipe ingredients, grocery lines and price lookups are all reconciled by string matching. Every silent-wrong-answer bug in the data layer traces back to this.

### Assessment of what Sonnet built

The feature surface is genuinely broad and the domain research (OSM `diet:*` coverage, FoodKeeper, HEI-2020, Portfolio diet, FSIS/openFDA) is real and correctly sourced. The layering is sane: models / schemas / services / routers, pure functions split from I/O, preview-then-confirm everywhere.

The failure is not breadth, it is **depth of root-causing**. The pattern is visible in the git log and in the code comments: a symptom is reported, a plausible mechanism is guessed, a defensive workaround is bolted on, and the workaround becomes permanent architecture. `ai_json_extraction.py` is 250 lines of bracket-scanning recovery machinery written to survive malformed model output — when Ollama has had server-side JSON-schema-constrained decoding the entire time, which makes malformed output *structurally impossible*. That one substitution deletes the whole module and most of the bugs it exists to paper over.

A second, related problem: the comments have become a commit log. Several files are 60–70% narrative about past debugging sessions. That is not harmless — it buries the logic, and it makes each new session re-read a history of wrong theories instead of the current behaviour.

### P0-1 — JSON extraction is hand-rolled when Ollama can constrain the output

`backend/app/services/ai_json_extraction.py`, all 13 AI call sites.

Every structured AI response in the app is free-form text that a bespoke parser then tries to rescue: strip `<think>` blocks, scan for balanced brackets, salvage truncated objects by cutting at the last top-level comma. This is the direct cause of the recipe-import history (three separate "root cause found" commits, all still leaving the feature broken).

Ollama supports `format: <JSON schema>` on `/api/chat`, which applies constrained decoding — the sampler is physically unable to emit a token that violates the schema. Ollama's own guidance is to pair it with `temperature: 0`.

**Consequence of not using it:** the extraction layer is a permanent source of intermittent failure that no amount of prompt tuning fixes, because the failure is in the sampler, not the prompt.

**Fix:** define Pydantic schemas for each extraction shape (recipe, inventory item list, meal plan, bloodwork, chat action envelope), pass `format=Model.model_json_schema()`, and validate with `Model.model_validate_json()`. Keep `ai_json_extraction.py` only as a fallback for a server too old to support `format`.

### P0-2 — Ollama calls have no timeout, on a single-threaded serial queue

`services/ollama_client.py:_client()` → `ollama.Client(host=base_url)`.

ollama-python's default `timeout` is `None`, which httpx interprets as *no timeout at all*. `services/job_queue.py` runs every AI job on one daemon thread with no cancellation, no per-job deadline, and no watchdog.

**Consequence:** one stalled generation — a model still loading into VRAM, a 27B model thrashing on an 11 GB card, a network blip to the host — wedges the worker thread **permanently**. Chat, recipe import, receipt import, vision intake, and meal-plan generation all stop working until the container is restarted, with the UI showing a spinner and no error. This alone is sufficient to produce "I haven't gotten reliable functionality from ANY component."

**Fix:** explicit `timeout=httpx.Timeout(connect=10, read=<configurable, default 600>, write=30, pool=10)` on the client; a job-level deadline in the worker; surface a timeout as job status `error` with a real message.

### P0-3 — A stale `job_id` in localStorage permanently disables the feature that stored it

`frontend/src/hooks/useBackgroundJob.js`, plus every page that does `disabled={job.busy}`.

On mount the hook reads a saved `job_id` and starts polling. If `GET /api/jobs/{id}` fails, the `catch` block **returns without changing state**, deliberately, and keeps polling forever. Status stays `"queued"`, so `busy` stays `true`, so the Import / Parse / Scan / Upload buttons stay disabled.

The job registry is in-memory (`_JOBS`) and capped at 100 entries. So the id goes 404 after *any* container restart, and also after 100 subsequent jobs. There is no user-visible way out — not a reload, not navigating away. Only clearing site data.

**Consequence:** exactly the "nothing works reliably" report. Every container rebuild during development would have silently bricked the import buttons on Inventory, Recipes and Health.

**Fix:** treat a 404 as terminal — clear the key and reset state. Add a consecutive-failure ceiling for transient errors. Persist the job registry (a small table, or at minimum a `resumable_until` timestamp) so a restart is distinguishable from "never existed".

### P0-4 — Barcode scanner cannot start on iOS/iPadOS

`frontend/src/components/BarcodeScanner.jsx:67-84`.

The component calls `BrowserCodeReader.listVideoInputDevices()` *before* any `getUserMedia()` call, then gates the second effect on the resulting `deviceId`.

WebKit deliberately withholds device identity until camera permission has been granted — labels are empty and `deviceId` values are obfuscated/empty on an unpermissioned origin. So `(rear || list[0]).deviceId` is `""`, which is falsy, so `if (!deviceId …) return;` fires and **the camera is never requested at all**. No permission prompt, no error, no video element. That is precisely the reported symptom, and it is unrelated to the HTTPS issue that was fixed on 2026-08-03 — this fails on HTTPS too.

**Fix:** call `navigator.mediaDevices.getUserMedia({ video: { facingMode: { ideal: "environment" } } })` first to trigger the prompt and unlock device labels, *then* enumerate to populate the camera picker. Or skip enumeration entirely on first run and use ZXing's `decodeFromConstraints` with `facingMode: "environment"`.

Two secondary bugs in the same file:
- The decode effect depends on `onDetected`, which the parent recreates every render — the camera tears down and restarts on every parent state change.
- If the component unmounts before the first decode callback fires, `controlsRef.current` is still null and the `MediaStream` leaks (camera light stays on).

### P0-5 — Receipt/vision extraction is sampled with settings that actively fight extraction

`backend/app/routers/inventory.py:238`

```python
_RECEIPT_EXTRA_OPTIONS = {"temperature": 0.7, "top_p": 0.8, "top_k": 20, "presence_penalty": 1.5}
```

These are Qwen's published **general chat** sampling parameters. They were applied to a deterministic list-extraction task.

- `temperature: 0.7` on extraction is wrong on its face; Ollama's own structured-output guidance says use `0`.
- `presence_penalty: 1.5` is the serious one. It penalises tokens that have already appeared. A receipt is a *highly repetitive* structure — the same JSON keys, the same units, the same `"category":` strings on every line. A strong presence penalty pushes the model to stop emitting that repeated structure. This is the most likely mechanism behind the documented "captured 4 of 8 real items from a 15-line receipt", and the penalty was *added while chasing that exact bug* — it made it worse.

Meanwhile the **recipe** import path passes no options at all, so it runs at Ollama's default `temperature: 0.8`. Two extraction paths, two different wrong sampling configs.

**Fix:** `temperature: 0`, no presence/frequency penalty, for every extraction call. Combined with P0-1 the sampling question largely stops mattering.

### P0-6 — Frontend Docker build copies the host's `node_modules` over the container's

`frontend/Dockerfile`:

```dockerfile
COPY package.json ./
RUN npm install
COPY . .          # <-- no .dockerignore exists anywhere in this repo
RUN npm run build
```

There is no `.dockerignore` in `frontend/` or `backend/`. `COPY . .` therefore copies the host's `frontend/node_modules` — plus `dist/`, two `dist.stale-*` trees, and ~45 `vite.config.js.timestamp-*.mjs` files — into the build stage, overwriting the `node_modules` that `npm install` just produced in the image.

**Consequence:** the build links against whatever binaries happen to be on the host, not the image. Non-reproducible builds, and a plausible contributor to "the fix still doesn't show up after redeploying" (which was previously attributed to caching and patched with `Cache-Control` headers — a symptom fix). `package-lock.json` is also never copied, so `npm install` re-resolves semver ranges on every build.

**Fix:** add `.dockerignore` files; `COPY package.json package-lock.json ./` + `npm ci`; pin the globally installed `http-proxy`/`serve-handler` versions.

### P1-1 — Dining Out: no dietary filtering, and the 50-result cap hides matches

`backend/app/routers/dining.py:69-95`, `services/dining_service.py`.

`evaluate_restrictions()` annotates each place with a verdict but nothing ever filters or sorts on it. Results are sorted by distance and then truncated: `places[:50]`.

**Consequence is worse than "no filter":** in any moderately dense area the 50 nearest restaurants are almost all untagged, and a genuinely `diet:gluten_free=only` place 3 km out is **cut off before the user ever sees it**. The one feature with real safety relevance is the one that discards the relevant results.

**Fix:** score first, truncate second. Sort by (restriction verdict rank, distance). Add a "only show places with a gluten-free tag" toggle and an explicit "N places nearby had no tag at all" count so absence of data stays visible.

### P1-2 — Dining Out: contact, website and map data is fetched and thrown away

`services/dining_service.py:parse_overpass_response`.

The Overpass query already uses `out tags center`, which returns **every** tag on each element. The parser reads `name`, `amenity`, `cuisine`, `addr:*` and `diet:*`, and discards `website` / `contact:website`, `phone` / `contact:phone`, `opening_hours`, and `wheelchair`.

The data is already on the wire and already paid for. This is a five-line parser change plus rendering. A map link needs no new dependency either — `lat`/`lon` are already present, so an OSM/Apple/Google link is a template string; an embedded map can be a Leaflet tile view later.

Also: the query matches `node` and `way` but not `relation`, so some multipolygon-mapped venues are missed.

### P1-3 — Unit conversion silently mistranslates tablespoons

`services/unit_conversion_service.py:normalize_unit`.

`UNIT_SYNONYMS` maps `"t" → "tsp"`, and `normalize_unit` lowercases before lookup. In standard recipe notation **`T` is tablespoon and `t` is teaspoon**. Lowercasing collapses the distinction and resolves both to teaspoon.

**Consequence:** `2 T butter` becomes `2 tsp` — a 3× error, applied silently to the display toggle, grocery aggregation, inventory deduction and cost math.

**Fix:** case-sensitive handling for the single-letter forms before lowercasing (`T`→tbsp, `t`→tsp, `C`/`c`→cup). If ambiguity can't be resolved, return the unit unrecognised rather than guessing — an unconverted line is recoverable, a 3× wrong one isn't.

### P1-4 — Failed unit conversions fall back to subtracting raw numbers

`services/inventory_service.py:deduct_by_name`, `services/meal_plan_service.py:subtract_inventory`.

Both do: try to convert; if `convert()` returns `None`, **subtract the numbers anyway as if the units matched.** This is documented in the docstrings as a deliberate fallback.

Concrete outcomes:
- Recipe needs `2 cup flour`; inventory row is `5 lb flour`. No density → conversion fails → on-hand becomes `3 lb`. Inventory now wrong.
- Grocery line needs `2 lb chicken`; inventory row is `500 g`. Conversion fails → `needed = 2 − 500 = −498` → **chicken is dropped from the grocery list**. You don't buy it.

The comment frames this as "a known, unchanged imprecision." It isn't imprecision, it's a wrong answer with no signal to the user.

**Fix:** when units are incomparable, do not do the arithmetic. Keep the grocery line at full quantity, skip the deduction, and attach a `needs_review` flag the UI surfaces. An unreconciled line the user can see beats a confidently wrong one.

### P1-5 — Ingredient matching is unbounded substring matching in both directions

`inventory_service.find_by_name`, `cost_service._find_priced_inventory_match`, `meal_plan_service.subtract_inventory`, `is_pantry_staple`.

Pattern: exact case-insensitive match, else `ILIKE %name%` — and in `subtract_inventory`, substring in *either* direction — taking the first row in arbitrary rowid order.

`"egg"` matches `"eggplant"`. `"oil"` matches `"oil-packed tuna"`. `"chicken"` matches `"chicken broth"`. There is no unique constraint on `inventory_items.name`, so duplicates accumulate and which one wins is undefined.

This is the join key for the entire app. It deserves better than `ILIKE`.

**Fix:** a real resolution layer — normalise (lowercase, strip punctuation, singularise), require word-boundary matches rather than raw substring, prefer the longest match not the first, and persist an alias table so a user correction is remembered. Return match confidence and let the UI ask when it's low.

### P1-6 — Chat and meal-plan prompts have no context budget and will silently exceed `num_ctx`

`services/chat_service.py:CHAT_CONTEXT_TEMPLATE`, `services/meal_plan_service.py:MEAL_PLAN_PROMPT_TEMPLATE`.

`content_char_budget()` exists and is applied to *imports only*. The chat prompt injects: a ~1200-token action-schema block, up to 80 inventory rows, up to **200** recipe titles, retrieved knowledge chunks, and the full conversation history. The meal-plan prompt injects 40 catalog recipes, 15 priority ingredients, health summary, knowledge chunks and 7×N slot lines.

Default `ollama_num_ctx` is 8192. Nothing measures the assembled prompt. Ollama silently truncates over-length input — the same failure mode that was already found and fixed once for imports, left unfixed for the two largest prompts in the app.

**Consequence:** chat and meal-plan generation degrade as the household's data grows, with no error — they just start ignoring the system prompt (which is at the front and gets clipped first) and producing junk.

**Fix:** run every prompt through a budget check before sending; log and truncate the *lowest-value* sections (catalog tail, oldest history) rather than letting Ollama clip the front. Set `num_predict` explicitly so response space is reserved.

### P1-7 — `format()` vs `replace()` inconsistency leaves two prompts able to crash at request time

`recipe_service.py` deliberately moved to `str.replace()` for the import prompt because a user-edited prompt containing a stray `{` would raise `KeyError` at request time. Correct reasoning — but `chat_service.CHAT_CONTEXT_TEMPLATE` and `meal_plan_service.MEAL_PLAN_PROMPT_TEMPLATE` still use `.format()`, and neither is GUI-editable yet. The moment they are exposed as editable settings (the stated B16 direction), the footgun is live.

Also: `meal_plan_service` imports `_extract_json_object`, `_safe_int` from `recipe_service`, and `chat_service` imports four private helpers from it. Private-by-convention functions crossing module boundaries in three directions.

### P1-8 — PDF recipe import has no empty-text guard and no OCR path

`recipe_service.extract_pdf_text` returns `"\n".join(page.extract_text() or "" for …)`.

For a scanned/image-only PDF that is the empty string, which is then interpolated into the prompt as an empty `SOURCE:` block. The model dutifully invents or refuses, and the user sees "Could not extract a recipe from that input" — indistinguishable from a parse failure.

**Fix:** if extracted text is below a threshold, either route the PDF's rendered pages to the vision model (the app already has that pipeline) or fail with an honest "this PDF has no extractable text — it looks scanned."

### P1-9 — `list_recipes` runs an allergen check per recipe

`routers/recipes.py:list_recipes` → `_to_read(r, db)` → `allergen_service.check_household_restrictions(db, …)` for every row, each re-reading household preferences. Classic N+1 on the page users open most.

**Fix:** load preferences once per request and pass them down; or add a `light=true` list projection that skips warnings.

### P2-1 — SQLite is configured with none of the settings that make it safe under threads

`backend/app/database.py`:

```python
connect_args = {"check_same_thread": False}
engine = create_engine(settings.database_url, connect_args=connect_args)
```

Missing:
- **`PRAGMA foreign_keys=ON`.** SQLite ignores foreign keys unless enabled per connection, and SQLAlchemy does not enable it. **Every FK in this schema is currently decorative.** Orphaned `recipe_ingredients`, `meal_plan_entries` and `knowledge_chunks` are possible on any delete path the ORM cascade doesn't cover.
- **`PRAGMA journal_mode=WAL`.** With the event loop, a `def`-route threadpool, and the job worker all writing, the default rollback journal serialises writers aggressively.
- **`busy_timeout`.** Default is 5 s from pysqlite; under concurrent writes this surfaces as `database is locked` 500s.
- `pool_pre_ping`, and a `NullPool`/`StaticPool` decision for the file-backed case.

**Fix:** a `connect` event listener issuing all three pragmas.

### P2-2 — `allow_origin_regex=".*"` with `allow_credentials=True`

`backend/app/main.py`. The comment explicitly chose to leave this permissive.

The practical exposure is currently limited because Starlette's `SessionMiddleware` defaults to `SameSite=Lax`, which blocks the cookie on cross-site `fetch`. But the CORS policy itself says "any origin on the internet may make credentialed requests to this API and read the response," and the backend ports are still published to the LAN. The safety here rests entirely on a default in a different middleware.

Given the frontend proxy now makes everything same-origin, the correct value is a concrete allow-list (or dropping CORS entirely and documenting direct API access as requiring no browser).

### P2-3 — Auth gate opens a DB session on every single API request

`main.py:auth_gate` is `async` and calls `SessionLocal()` + `auth_service.is_enabled(db)` synchronously — i.e. blocking I/O on the event loop, on every `/api/*` request including the 1.5 s job poll and the jobs badge poll.

**Fix:** cache the enabled flag in module state, invalidated when the password is set/cleared.

### P2-4 — `env_file: .env` is mandatory, so a fresh clone fails to start

`docker-compose.yml` declares `env_file: - .env` for both services with no `required: false`. A new user who clones the repo and runs `docker compose up --build` without first copying `.env.example` gets a hard failure. The README's stated goal is that external users can pull down and run this.

Related: no `healthcheck` on either service, and `depends_on: backend` without `condition: service_healthy` — the frontend proxy can begin serving before migrations finish.

### P2-5 — `datetime.utcnow()` is deprecated and naive

`models/base.py:TimestampMixin` and several services. Deprecated in Python 3.12 (the image's interpreter), and produces naive datetimes that are compared against timezone-aware values elsewhere. Use `datetime.now(timezone.utc)`.

Note also: the repo's `__pycache__` files are `cpython-310`, so local test runs have been on 3.10 while the image and CI run 3.12.

### P2-6 — Knowledge indexing runs synchronously on the request path

`knowledge_service.ensure_indexed` is called lazily before retrieval, which happens inside chat and meal-plan generation. A stale index means a full re-embed of the corpus — N sequential Ollama `embeddings` calls, on the job worker, with no timeout (see P0-2). This is a second way to wedge the queue.

**Fix:** make reindex its own queued job; retrieval should use whatever index exists and report staleness rather than block.

### P2-7 — `http-proxy` is unmaintained and unpinned; no proxy timeouts

`frontend/Dockerfile` does `npm install -g http-proxy serve-handler` with no versions. `http-proxy` (v1.18.x) has been effectively unmaintained for years. `server.js` sets no `proxyTimeout`/`timeout`, so a slow backend response holds the socket indefinitely.

**Fix:** pin versions; consider `http-proxy-middleware` or Node's built-in `fetch` piping; set explicit proxy timeouts and a body size limit.

### P2-8 — Service worker caches every non-API GET forever with no version discipline

`frontend/public/sw.js`. Network-first with cache fallback and unbounded cache growth; the navigation fallback looks up `/index.html` but navigations to `/` are keyed as `/`. `CACHE_VERSION` is a hand-maintained `"v1"` that has never been bumped.

This is a plausible contributor to the "redeploy doesn't take effect" reports that were previously addressed by adding `Cache-Control` headers.

## 4. One more P0, found while implementing

### P0-7 — Installing a TLS certificate broke every API call

`backend/app/run_server.py` vs. `frontend/server.js`.

Two changes made a week apart contradicted each other, and nothing tested the combination.

B15.1 (2026-08-01) made the backend serve HTTPS on `BACKEND_HTTPS_PORT` and turn `BACKEND_PORT` into a **307-redirect-only** listener whenever a certificate is present.

The 2026-08-03 proxy rework then pointed the frontend's reverse proxy at `http://<backend>:$BACKEND_PORT` over the internal Docker network.

So the moment a certificate is installed, every proxied API call gets back `307 → https://backend:8446/...` — an internal Docker hostname no browser on the LAN can resolve. **Installing the certificate that B15.1 exists to provide (and that the camera and geolocation both require) silently broke the entire API.**

That is very likely a large part of "I haven't gotten reliable functionality from ANY component," since the iPad testing that motivated B15.1 would have been done with a certificate installed.

**Fixed:** TLS now terminates once, at the frontend edge the browser actually talks to. The backend keeps its own HTTPS listener for direct access and always serves the real app on plain HTTP internally. The only thing given up is the backend's own HTTP→HTTPS bookmark redirect, which only ever mattered for hitting the API directly in a browser.

#### P1-5, as built

**Matching.** Names normalise to token sequences (case, accent, punctuation folding; conservative singularisation with an explicit never-singularise list; a second "core" form with preparation words and bare numbers removed). Comparison is by whole token, never substring — which is what makes `"egg"` vs `"eggplant"` score **zero** rather than merely low, since they share no token at all.

**Transformation head-nouns.** A curated list (broth, stock, oil, milk, flour, extract, …) of words meaning "a product made FROM the other ingredient". Present on one side and not the other, the pair is *blocked* outright, not downranked: `"chicken"`/`"chicken broth"` and `"almond"`/`"almond milk"` are different foods no matter how much text they share. The list is non-exhaustive by construction, so it is user-editable from Settings (`ingredient_transformation_words`); getting it wrong is safe in both directions — a missing word downgrades a match to a confirmable suggestion, an extra one produces a question rather than a wrong answer.

**Head agreement.** English food compounds are head-final, so a token subset that is a *suffix* ("oil" in "olive oil") is a narrowing match at high confidence, while a subset that is not ("oil" in "oil-packed tuna", "chicken" in "chicken breast") is a suggestion at low confidence. Those last two are structurally identical and nothing in the strings separates them, so both are surfaced and neither is applied — which is what the alias table exists to resolve permanently. One exception is capped just under the write threshold: when the shared head noun is itself a transformation word, the qualifier may name the source ("olive oil" is oil, "peanut butter" is not butter), so that whole family asks once.

**Determinism.** `inventory_items.name` has no unique constraint (two cartons of milk with different dates are two legitimate rows), so ties are broken on purpose rather than by rowid: stocked rows before empty ones, then soonest expiration — first-expired-first-out, which is also what `compute_urgency` already argues the app should prefer. `cost_service` deliberately uses a *different* tiebreak (most recently purchased priced row), because "what did this last cost" is a different question from "which carton should we use up".

**Confidence policy, per call site.** Three thresholds, in one place, set by what a wrong answer costs:

| Call site | Bar | Below it |
|---|---|---|
| `deduct_by_name`, `update_by_name` | high | 409 with ranked candidates, **nothing written** |
| `subtract_inventory`, `cost_service` | medium | line keeps full quantity; cost line unresolved |
| `is_pantry_staple` | high | not a staple |

`is_pantry_staple` is at the strict bar despite the old code's comment arguing it was low-stakes. A staple hit removes a line from the grocery list *entirely*, before any quantity math — the failure mode is arriving at the stove without an ingredient, with nothing on screen to notice. It also now queries staple-first (generic covers specific, the direction households actually write staples), so `"salt"` still covers `"kosher salt"` while `"oil"` no longer covers `"oil-packed tuna"`.

**Alias table.** `ingredient_aliases`, migration `f1a4d7c93b28`. Aliases resolve to a *name*, not a row id, so they survive the item being used up and re-bought; an optional `inventory_item_id` pins a specific row and is `SET NULL` on delete. Chains are bounded and cycle-guarded. Nothing is seeded — a starter list would mean asserting food equivalences this project has not verified.

**Surfaced to the UI.** `GET /api/inventory/resolve` (read-only), alias CRUD, 409-with-candidates on both write endpoints with `item_id`/`remember_alias` to answer. `IngredientMatchPicker` renders the question inline on chat action cards; confirming a meal reports every ingredient it could *not* deduct instead of skipping silently; grocery lines now carry `matched_item_name`/`match_confidence`. Same migration also persists `needs_review` — P1-4's explanation was computed and then discarded before reaching a row, so no user had ever actually seen one.

**Not attempted, deliberately:** fuzzy/edit-distance matching. A typo threshold loose enough to fix `"tomatos"` also makes `"cumin"` match `"cumin seed"` and `"butter"` match `"batter"`. Given a wrong answer here silently corrupts inventory, refusing to match is the better failure — and the alias table means each refusal is answered at most once.
