# Chef App — Project Plan & Grounding Notes

Living document. Read this first in any new session to recover context. Update it whenever a phase completes, a decision is made, or something is discovered that the next session needs to know.

## What this is

A locally hosted, AI-driven, web-connected meal planning, food inventory, and recipe management app for a household (default 2 people). Runs via Docker Compose. Ships on GitHub so others can pull it down and self-host. Uses Ollama for local LLM inference and Tavily for web search grounding.

## Origin note

This project supersedes an earlier prototype built inside a personal "Local AI" Open WebUI stack (Ollama + mcpo + ComfyUI + n8n + a `chef-api` container, Excel workbook as datastore). That prototype is not part of this repo. Some of its design patterns (interactive tool surface, autonomous weekly meal-plan job, avoiding spreadsheet-as-database) were salvaged and are reflected in the decisions below.

## Architecture decisions (confirmed 2026-07-30)

| Decision | Choice | Why |
|---|---|---|
| Backend | Python + FastAPI | Best local-LLM/Ollama ecosystem support, async, auto API docs, matches prior prototype's language |
| Frontend | React (Vite) SPA | Needed for a chat panel that stays alive across page navigation; richer interactivity for inventory/recipe editing |
| Database | SQLite (file-backed, via SQLAlchemy + Alembic) | "Lightweight local DB" per project brief; avoids the Excel file-locking problem hit in the prior prototype |
| Styling | Single centralized CSS (CSS variables / design tokens) imported app-wide | Project brief requires one-source theming |
| Containerization | Docker Compose: `backend`, `frontend` services, SQLite + uploaded images on a named volume for persistence across rebuilds | Required by project brief |
| LLM | Ollama, base URL configurable via `.env` / Settings GUI (defaults to `http://host.docker.internal:11434`, override for a containerized Ollama) | Author already runs Ollama in his environment |
| Web search | Tavily API, key entered via Settings GUI or `.env`, never hardcoded | Author has an existing key |
| Settings/secrets storage | Database (`AppSetting` table), not `.env`. `.env` only for infra bootstrap (`DATABASE_URL`, ports) plus optional first-run seed convenience. Secrets encrypted at rest with Fernet, key rotation supported | Author's explicit preference (2026-07-30), matching the pattern already validated in the sibling Fiduciary project — see "Settings & secrets storage" section below |

Open question for a future session: does the author want Ollama itself running inside this repo's Docker Compose (with GPU passthrough configured for the 1080 Tis), or does it stay a separate/host service that this app just points at? Scaffolding currently assumes the latter (external Ollama) since "Ollama is available in the environment" was stated as a given. Revisit if the author wants it bundled.

## Phase 3 notes: inventory

Backend (`backend/app/routers/inventory.py`, `app/services/inventory_service.py`, `app/schemas/inventory.py`):

- Full CRUD: `GET/POST /api/inventory`, `GET/PATCH/DELETE /api/inventory/{id}`, with `category`/`is_priority`/`search` filters on the list endpoint.
- **Urgency scoring** (`compute_urgency`): points for expired (100) / expiring ≤3d (80) / ≤7d (50) / ≤14d (20) days, staleness (unused >60d: 30, >30d: 15), and the `is_priority` flag (25) — plus human-readable reasons. `GET /api/inventory/priority-suggestions` returns items ranked by this score; the meal-planning engine (Phase 5) is meant to consume the same function directly, not just the endpoint.
- **Vision photo intake**: `POST /api/inventory/vision-intake` sends the uploaded image + a JSON-array-only prompt to the configured Ollama vision model and returns a *preview* (nothing written to inventory yet). `POST /api/inventory/vision-intake/confirm` bulk-creates from a (user-reviewed/edited) item list. Response parsing (`parse_vision_response`) is defensive — tries strict JSON, falls back to extracting the first `[...]` block — because real vision-model output often wraps JSON in prose/markdown fences; unit-tested against both cases plus garbage input and an invalid category value.
- **Deduction primitive** (`deduct_by_name`): case-insensitive exact-then-substring match against inventory by name, decrements quantity floored at 0, stamps `last_used_date`. This is what Phase 5 (confirming a meal-plan entry) and Phase 7 (chat: "we made X" / "we're out of Y") will call — matching recipe ingredient names to inventory names is inherently fuzzy; a smarter matcher (aliases, unit conversion) is a documented future improvement, not attempted here.

Frontend (`frontend/src/pages/InventoryPage.jsx`, `components/InventoryItemForm.jsx`): category filter, add/edit form (shared component), delete, and a photo-upload flow that shows the detected-items preview before anything is committed. Rows are color-coded by urgency score using the same reasons the backend computed. Switched to `HashRouter` (was a single static page) with a nav bar for Home/Inventory.

**Known simplification: frontend/backend origins.** Docker Compose runs `frontend` (5173) and `backend` (8095) as separate containers with no reverse proxy between them. In dev (`npm run dev`), the vite proxy in `vite.config.js` makes `/api/*` and `/health` same-origin. In the production Docker build, `frontend/src/api.js` falls back to hitting the backend directly at `${hostname}:8095` (hardcoded port, matching `.env`'s `BACKEND_PORT` default) using the backend's wide-open CORS. This works for the common single-host case but is fragile if `BACKEND_PORT` is changed without updating `api.js` too, and doesn't support serving over HTTPS/a real domain cleanly. A shared reverse proxy (nginx/Caddy sidecar, single external port) is a reasonable Phase 9 packaging improvement.

**Verification:** unit tests for `parse_vision_response` (4 cases) and `deduct_by_name` (exact match, fuzzy match, no match, floor-at-zero) run directly against the service module; full CRUD + priority-suggestions + bulk vision-confirm exercised via curl against a live local uvicorn instance; `vision-intake` itself confirmed to fail cleanly with a 502 (no live Ollama in the sandbox) rather than crashing. Frontend: `npm run build` succeeds; ran the real Vite dev server against the real backend together and hit `/health` and `/api/inventory` (including a POST) through the actual proxy path the browser will use, not just each side in isolation.

## Operational note: bash sandbox / native file coherence

Claude's bash sandbox sees this folder through a FUSE mount that can cache stale file sizes -- if Claude edits a file with the Read/Write/Edit tools and then reads/git-adds/executes it via bash in the same session, the bash side can occasionally get truncated/stale content instead of the true file (documented and verified in the sibling Fiduciary project, `docs/COWORK-FUSE-COHERENCE.md`). Checked on 2026-07-30: every file that had been through this mixed edit pattern so far (`config.py`, `main.py`, `.gitignore`, `README.md`, `.env.example`, `seed.py`, this file) was verified intact -- Read tool content matched `git show HEAD:<path>` exactly, no corruption found. Going forward, prefer a single writer surface (bash heredoc/sed, or the Edit/Write tool) per file for its whole edit-test-commit cycle, and spot-check with the Read tool before trusting a bash-side commit of a file that was just edited natively.

### B1 -- Nutrition data integrity (highest-value gap)

The single largest correctness gap in the app today: `Recipe.nutrition` is a free-form JSON dict populated entirely by whatever the LLM estimated at import/generation time. Nothing in the codebase references an authoritative food-composition source. Every downstream feature the brief cares about (cholesterol steering, calorie counts, BMI-aware portioning) currently rests on a hallucination-prone number that is never checked. Published research on LLM nutrition advice makes the same point: models that do not encode population reference-intake data can produce recommendations without appropriate nutritional constraints.

- [x] **B1.1 -- Ingredient-to-food-database resolution layer.** Done 2026-07-31 -- see notes section below. New service that maps a `RecipeIngredient` name+quantity+unit to a canonical food record and returns per-100g nutrients. Primary source: USDA FoodData Central (free, government-backed, ~300K+ foods, API key required, no barcode/branded coverage). Secondary: Open Food Facts (free, crowd-sourced, ~2.5M+ products, has barcodes) for packaged/branded items USDA lacks. Both are free and self-host-friendly, which matters for a project meant to be pulled down by external users -- Edamam/Nutritionix/Spoonacular are all paid past a low free tier and would put a per-user API bill in front of anyone cloning the repo. Store the resolved FDC id / OFF barcode on the ingredient row so a resolution is done once, not per request.
- [x] **B1.2 -- Computed vs. estimated nutrition, visibly distinguished.** Done 2026-07-31 -- see notes section below.
- [x] **B1.3 -- Expand the nutrition dict, and reconcile the two prompts that disagree about it.** Done 2026-07-31, together with B1.2 -- see notes section below. Added saturated fat and total sugars (both cleanly available from USDA/OFF); added_sugars_g and soluble_fiber_g were investigated and deliberately NOT added -- neither source cleanly distinguishes them from total sugars/fiber, and this app doesn't mislabel one nutrient as another.
- [x] **B1.4 -- Daily and weekly nutrient roll-up.** Nothing currently sums a day or a week. Add a per-day and per-week nutrition view over a `MealPlan`, compared against DRI-derived targets computed from each `HouseholdMember`'s age/sex/height/weight/activity (all already in the schema and unused for this). This is the feature that turns logged body metrics into an actual feedback loop rather than a chart nobody acts on. **Completed 2026-08-01 -- see notes section below.**

### B2 -- Diet-quality scoring and guideline grounding

- [ ] **B2.1 -- Ship curated guideline knowledge files as repo defaults.** The knowledge/RAG plumbing exists and works, but the repo ships with an empty corpus, so every external user starts ungrounded and the "grounded in nutritionist knowledge" requirement is technically unmet out of the box. Bundle a small set of public-domain/openly-licensed reference documents seeded as inactive-by-default knowledge files the user can toggle on: Dietary Guidelines for Americans, DRI reference tables, cholesterol-specific patterns (Portfolio diet, DASH, Mediterranean), **and official food-allergy/allergen research** (author-requested 2026-07-31) -- e.g. NIAID's Guidelines for the Diagnosis and Management of Food Allergy, and FDA/FALCPA-and-FASTER-Act major-allergen reference material (the nine major allergens: milk, eggs, fish, crustacean shellfish, tree nuts, peanuts, wheat, soybeans, sesame). This corpus doubles as reference grounding for B3.1/B3.2's structured allergen/cross-contact model, not just free-text dietary advice. Check licensing per document before bundling; US federal/NIH government works are generally public domain but verify each.
- [ ] **B2.2 -- Diet-quality score on a generated plan.** HEI-2020 (Healthy Eating Index, 0-100, 13 components: 9 adequacy, 4 moderation) is the standard, published, computable US diet-quality metric -- the national average is 58/100, so there is a real reference point to show against. Scoring a generated week gives the planner an objective quality signal instead of "the model said it was balanced," and gives the user a single number that moves. Requires B1.1/B1.3 first (needs real food-group and nutrient data).
- [ ] **B2.3 -- Portfolio-diet-aware LDL steering.** The author's stated goal is LDL reduction. The Portfolio diet is the pattern explicitly engineered for that (plant sterols, viscous/soluble fiber, nuts, soy protein), overlapping but more targeted than DASH or Mediterranean. Add it as a selectable dietary goal preset that concretely biases ingredient selection, rather than leaving "reduce cholesterol" as free text in the goals field for the model to interpret differently every week.

### B3 -- Celiac and allergen safety

- [x] **B3.1 -- First-class allergen/restriction model.** Dietary restrictions are currently free-text JSON on `HouseholdPreferences`, interpreted by the LLM per prompt. Nothing structurally prevents a generated plan or an imported recipe from containing gluten. Add a structured allergen/restriction taxonomy and a deterministic (non-LLM) check that flags any recipe or plan entry containing a restricted ingredient, run at import, at plan generation, and at plan confirm. **Completed 2026-07-31 -- see notes section below.**
- [x] **B3.2 -- Cross-contact awareness, not just ingredient matching.** Best-in-class celiac tools (Fig, Spoonful) go beyond the label: Fig lets the user set an observance level (must avoid gluten and cross-contamination not ok / gluten only / trying to avoid), and Spoonful flags cross-contact risks such as non-certified oats. Chef should carry the same observance-level setting and flag known cross-contact ingredients (oats, shared-equipment items, bulk-bin staples) rather than treating "no wheat in the ingredient list" as safe. This is a genuine safety feature for the stated primary user, not a nicety. **Completed 2026-07-31 -- see notes section below.**
- [ ] **B3.3 -- Recall awareness.** The USDA FSIS Recall API and the openFDA food enforcement API are both free and public; USDA's own FoodKeeper app pushes recall notifications. A daily/weekly check of current inventory item names and brands against active recalls is a differentiator essentially no consumer meal planner offers, and is cheap given inventory is already structured.

### B4 -- Inventory capture friction

Inventory quality determines whether every other feature works, and manual entry is where these apps die. Chef currently has manual entry, vision photo intake, and chat -- but not the two mechanisms that dominate the category.

- [ ] **B4.1 -- Barcode scanning to Open Food Facts.** Tandoor does exactly this (scan, look up in OpenFoodFacts, get name and nutrition). A browser-based scanner (`BarcodeDetector` API with a JS fallback) plus an OFF lookup gives near-zero-friction addition of packaged goods and pulls in nutrition data for free -- shares the B1.1 resolution layer.
- [x] **B4.2 -- Grocery receipt OCR intake.** The category standard is now a receipt photo that populates inventory automatically with quantities and prices; the leading apps claim 95%+ line-item accuracy. Chef already has a vision model wired up and an established preview-then-confirm intake pattern, so this is largely a new prompt plus a review screen, not new architecture. Biggest win per unit of effort in this group. **Completed 2026-08-01 -- author-requested directly (receipt photo/PDF, or a plain-text/file list of purchased items), generalized beyond photo-only OCR. See notes section below.**
- [ ] **B4.3 -- FoodKeeper-backed default shelf life.** USDA publishes FoodKeeper as a machine-readable data feed covering storage guidance for 500+ food and beverage items. Use it to auto-suggest an expiration date when the user adds an item without one -- directly serving the brief's "keep expiration information as much as reasonably possible" and the stated forgotten-pantry-item problem, which currently depends on the user remembering to type a date.
- [x] **B4.4 -- Expiration notifications.** Every competitor in the food-waste space notifies ahead of expiry (typically 7 days out and on the day) with color-coded status. Chef computes urgency server-side already but only surfaces it passively when the user opens the Inventory page. Add a digest (in-app banner at minimum; optional email/webhook) so the app reaches out rather than waiting to be visited. **Completed 2026-08-01 as part of B10.2 -- the in-app banner (the stated minimum); push/email deliberately not built, see B10.2's notes section.**

### B5 -- Meal-plan mechanics

- [ ] **B5.1 -- Explicit leftovers modeling.** The brief says "leftovers welcome" and the author cooks for two; the plan engine has no concept of one cook event feeding multiple slots. Plan to Eat schedules leftovers as first-class calendar items and Eat This Much merges cook events to cut stove time. Add a leftover/portion link between plan entries so a Sunday cook can legitimately fill Monday lunch, with inventory deducted once rather than twice.
- [ ] **B5.2 -- Prep-day / batch-cooking mode.** Mealime Pro's "Meal Prep Day" batch-cooks proteins and grains for mix-and-match assembly; MealPrepPro builds whole weeks around a single cooking afternoon. Add a generation mode that clusters shared components into one prep session, then composes weekday meals from them. Fits the author's stated quick-preparation preference better than seven independent cook events.
- [x] **B5.3 -- Unit conversion layer.** Core conversion table built 2026-07-31 (`unit_conversion_service.py`) and wired into `inventory_service.deduct_by_name` and `meal_plan_service.aggregate_ingredients`/`subtract_inventory` the same day. The two remaining pieces -- the B10.5 recipe-detail-page toggle UI, and density-sourcing for the volume<->mass ("weight mode") case -- were completed together with B10.5 on 2026-08-01 (see that item's notes section). Already documented as a known simplification in the Phase 5 notes: "2 cup flour" and "1 lb flour" stay separate grocery-list lines and inventory deduction is name-match-only when no density is available. Public recipe-scaling APIs exist that return smart culinary fractions and unit promotion, but a local density/unit table was the right call for an offline-first app.
- [x] **B5.4 -- Grocery list grouped by store aisle.** `GroceryListItem.category` was added in Phase 5 explicitly "for a future group-by-aisle view" and is still unused. Tandoor implements supermarket aisle mapping with per-store section ordering. Low effort, high daily-use payoff. **Completed 2026-08-01 -- see notes section below.**
- [ ] **B5.5 -- Pantry-staple exclusion from the grocery list.** Aggregation currently only omits a quantity-less ingredient ("salt to taste") when something matching exists in inventory. A user-maintained "always on hand" staple list would stop obvious noise (salt, pepper, oil) from appearing every week.

### B6 -- Cost and budget

- [ ] **B6.1 -- Cost per recipe and cost per serving.** Tandoor does meal-cost calculation; the notable 2026 critique of AI recipe apps is that they are price-blind. Even a manually-entered or receipt-derived (B4.2) price-per-unit on inventory items would let Chef show cost per serving and a projected weekly grocery spend -- a metric households actually make decisions on. **Partially unblocked 2026-08-01**: `InventoryItem.unit_price` now exists and is populated by the B10.3 order-history importer (and editable manually) -- the price DATA this item needs is now capturable; the actual cost-per-recipe/weekly-spend computation and display is still not built.
- [ ] **B6.2 -- Live retailer pricing (investigate only, do not commit).** Kroger publishes a public developer API but only for its own stores; Walmart publishes none; Instacart pricing is available through third-party/scraper services. Scraping is out of scope for a self-hosted app shipped to strangers. Recommendation: treat B6.1 (user/receipt-sourced pricing) as the real deliverable and keep retailer APIs as an optional per-user configured integration at most.

### B8 -- Health data integration

- [ ] **B8.1 -- Bloodwork import instead of hand entry.** Metrics are typed in one field at a time. A CSV/PDF lab-panel import (the app already extracts text from PDFs for recipes and knowledge files) would make trend tracking realistic rather than aspirational.
- [ ] **B8.2 -- Wearable/health-platform import (opt-in, file-based first).** Apple Health, Google Health Connect, and Withings all export; aggregator APIs (Terra and similar) cover 500+ devices but are paid and cloud-dependent, which fits this project's local-first stance badly. ## Settings & secrets storage

Ported from `Fiduciary/portfolio-api/secrets_crypto.py` (a validated, tested module in the author's sibling project, read directly on 2026-07-30 — not reinvented from scratch) into `backend/app/services/secrets_crypto.py`:

- Fernet (AES-128-CBC + HMAC, via the `cryptography` package) symmetric encryption for any `AppSetting` row where `is_secret=True` (currently just `tavily_api_key`).
- Key file at `/app/data/secrets.key` (same Docker volume as the SQLite DB), generated on first run, written atomically with 0600 permissions. **Losing this file makes every encrypted value permanently unrecoverable** — back it up alongside `./data`.
- Versioned envelope encryption from day one so key rotation is possible later without a bulk re-encrypt: unrotated deployments produce unprefixed ciphertext (the common case); `rotate_key()` adds a new key version to `/app/data/secrets_keyring.json`, all new encrypts use it, old ciphertext keeps decrypting under its original key forever.
- `decrypt_or_legacy()` never raises — falls back to returning the raw value if it isn't a valid token, for defensive handling of pre-encryption data.

`backend/app/services/settings_service.py` wraps this with a `SETTING_SPECS` registry (key, label, `is_secret`, default, description, optional `.env` fallback name) and `get_setting()`/`set_setting()`/`list_settings_for_display()` (secrets masked as `********` for API responses). `app/seed.py` uses this to seed each setting once — from an optional `.env` value if present, otherwise the spec default — and never overwrites a value that already exists, whether set via `.env` or later via the Settings UI (Phase 8).

`app/config.py` (pydantic `Settings`) now holds ONLY true infra bootstrap values (`database_url`, `backend_port`) that must exist before the DB is reachable. Everything else moved out of it: Ollama base URL/models and the Tavily key are DB-backed via `settings_service`; household size lives in `HouseholdPreferences` (already the case since Phase 1).

`app/services/ollama_client.py` and `app/services/tavily_client.py` are thin wrappers that pull their config from `settings_service` per-call (not cached at import time), so a Settings UI edit takes effect on the next request without a restart.

**Known sandbox-only quirk (not a bug):** importing the `ollama` package fails inside Claude's sandbox because ambient `ALL_PROXY=socks5h://...` env vars (from the sandbox's own network setup) break `ollama`'s eager default-client construction at import time. Confirmed this doesn't happen with those proxy vars unset, and the real Docker deployment won't have them set. Local verification of `ollama_client.py`/`tavily_client.py` therefore ran with `env -u ALL_PROXY -u ...`; no code changes were needed to work around it.

**Generation** (`POST /api/meal-plans/generate`): same preview-then-confirm pattern as recipe import -- returns a `MealPlanCreate`-shaped preview, nothing persisted until the user reviews/edits and `POST`s to `/api/meal-plans`. `meal_plan_service.gather_generation_context()` pulls together everything the model needs to ground a sensible plan: household size/dietary restrictions/goals/indulgence frequency, the active (or requested) kitchen profile's equipment list, `inventory_service.get_priority_suggestions()` (the same urgency-scoring function built in Phase 3, reused directly rather than reimplemented) for what to prioritize using up, and a compact recipe catalog (staples and highly-rated first) so the model can reuse an existing recipe instead of inventing one for every slot. Per-slot guidance (e.g. "Saturday lunch needs to be portable for a picnic") and free-text notes (e.g. "going camping this weekend") can steer generation.

**Defensive parsing carries a validation step recipe import didn't need**: `parse_meal_plan_response()` coerces fields the same defensive way as recipe import (strict JSON first, then extract the first `{...}` block), but a meal plan additionally references *existing* recipe ids the model was shown -- and models sometimes hallucinate one that wasn't in the catalog. `validate_entries_against_catalog()` nulls out any `recipe_id` not actually present in the catalog that was sent, rather than trusting it; the slot is then left recipe-less for the user to fix in the review step, same as any other AI-preview-then-confirm flow here. Verified with a live curl test using a mocked Ollama response that deliberately includes a fabricated id (999) alongside two valid slots (one reusing a catalog recipe, one proposing a `new_recipe`) -- confirmed the hallucinated id came back `null` while the other two passed through correctly.

**Grocery list derivation**: split the same way as recipe import's URL extraction -- a pure aggregation/subtraction pair (`aggregate_ingredients`, `subtract_inventory`) that's unit-testable without a DB, plus a thin `compute_grocery_list()` wrapper that loads a persisted plan's entries/inventory. Ingredients are scaled to each entry's servings (reusing `recipe_service.scale_ingredients`), summed across all non-skipped entries keyed by `(name, unit)`, then matched against current inventory the same case-insensitive exact-then-substring way as `inventory_service.deduct_by_name` and subtracted; only the remaining (still-needed) quantity is listed. An ingredient with no stated quantity (e.g. "salt to taste") is only listed if nothing matching exists in inventory at all, rather than always appearing. Recomputation happens automatically on plan creation, on any entry edit/skip (`_persist_grocery_list()` replaces `source="auto"` rows only, leaving manually-added items alone), and on-demand via `POST /{plan_id}/grocery-list/regenerate` (e.g. after a shopping trip). Verified: confirming a meal deducts its scaled ingredients from inventory (reusing `inventory_service.deduct_by_name` once per ingredient) and a subsequent grocery-list regeneration correctly reflects the now-lower on-hand quantity -- i.e. the grocery list always answers "what do I still need to buy for everything not yet skipped," not a frozen snapshot from generation time.

**New-recipe creation on confirm**: `recipe_service.create_recipe_from_parsed()` (new, shared) creates a `Recipe` + ingredients + tags from a `coerce_recipe_fields()`-shaped dict without duplicating `routers/recipes.py`'s creation wiring wholesale -- used when `POST /api/meal-plans` persists an entry whose slot had no catalog match, tagging the new recipe `source="ai_generated"`. Verified live: a generated plan's `new_recipe` entry actually appears in `GET /api/recipes` afterward with the correct source label and is immediately available for future weeks' catalogs.

**Confirm/skip**: `POST /{plan_id}/entries/{entry_id}/confirm` marks a meal as made and deducts its scaled ingredients from inventory (best-effort -- an ingredient with no inventory match is silently skipped rather than failing the whole confirmation); `/skip` marks it skipped with no deduction. Both are blocked once an entry is already confirmed (400), and skip is blocked on an already-confirmed entry, verified via live curl including the double-confirm 400 case. Deleting a plan cascades to its entries (existing `cascade="all, delete-orphan"` relationship from Phase 1), verified live.

Frontend (`frontend/src/pages/MealPlanPage.jsx`, `components/MealPlanEntryRow.jsx`, `components/GroceryListPanel.jsx`): a plan picker (dropdown over existing plans by week), a generate form (week start date, household size override, kitchen profile select, meal-type checkboxes, free-text notes, and a collapsible per-day tags/notes guidance section), an editable review step after generation (swap any slot between the AI's proposed new recipe and any catalog recipe, adjust servings/tags/indulgence flag, nothing saved until confirmed), a weekly grid for the persisted plan (recipe swap, servings, "we made this"/skip actions, linking through to the recipe detail page), and a self-contained grocery list panel (checkbox to mark purchased, manual add, delete, recompute-from-inventory). ## Phase 6 notes: health & nutrition tracking

Backend (`backend/app/routers/household.py`, `app/routers/health.py`, `app/routers/knowledge.py`, `app/services/health_service.py`, `app/services/knowledge_service.py`, `app/schemas/household.py`, `app/schemas/health.py`, `app/schemas/knowledge.py`):

**Schema** (migration `a4a23dff4e5e`): `KnowledgeFile` gained `content` (Text, nullable -- extracted plain text, populated once at upload rather than re-parsed on every request) and `is_active` (Boolean, default true -- only active files ground generation). `HouseholdPreferences`, `HouseholdMember`, and `HealthMetricEntry` already existed from the Phase 1 schema but had no API until now.

**Household preferences & members** (`routers/household.py`, new): `GET/PATCH /api/household/preferences` for the singleton row (household size, dietary restrictions, goals, indulgence frequency), `GET/POST /api/household/members` + `PATCH/DELETE /api/household/members/{id}` for per-person profiles (age, height, sex, activity level) that both BMI calculation and meal-plan generation draw on.

**Health metrics & BMI** (`routers/health.py`, new): `GET/POST /api/health/metrics` (optionally filtered by member) and `PATCH/DELETE /api/health/metrics/{id}`. BMI is deliberately never accepted from the client -- `_compute_bmi_for_entry()` always computes it server-side from the submitted `weight_kg` and the associated member's `height_cm` (`health_service.compute_bmi`), so it can't drift out of sync if the member's height is corrected later, and is recomputed on any `PATCH` that changes `weight_kg` or `household_member_id`. Weight is stored canonically in kg (matches the existing model); the frontend (`HealthPage.jsx`) converts to/from pounds for display and entry, since a US household is the primary near-term user, without baking imperial units into the schema.

**Trend computation** (`GET /api/health/trends?household_member_id=`): `health_service.compute_metric_trend()` compares the most recent data point for a field against the oldest point still within a rolling window (default 90 days), falling back to the earliest point overall if none fall inside the window -- e.g. "down 3.5kg over the last 90 days" rather than a naive first-vs-last-ever comparison that could span years. Returns `null` for a field with fewer than 2 data points rather than a misleading zero-delta. Covers weight, BMI, LDL, HDL, and total cholesterol in one response.

**BMI/health-aware meal planning**: `health_service.build_health_context_summary()` builds a compact per-member line (e.g. "Jason: weight 94.5kg, BMI 29.2 (overweight), LDL 128.0 mg/dL ... weight down 3.5kg over the last 90 days") from the same trend function, and `meal_plan_service.gather_generation_context()` (Phase 5) now includes it as `health_summary`, injected into the generation prompt via a new section instructing the model to let it quietly bias toward lower-cholesterol, appropriately-portioned choices without mentioning the numbers directly to the user. This directly closes the loop the project brief asked for: body metrics actually steering plan generation, not just being logged and forgotten.

**Nutritionist knowledge files** (`routers/knowledge.py` + `services/knowledge_service.py`, new): `POST /api/knowledge-files` (multipart upload) stores the raw file on disk under a UUID-based name (`knowledge_service.save_file`, same atomic-write pattern as `secrets_crypto.py`'s key file, avoiding filename-collision/traversal issues from user-supplied names) and extracts plain text once at upload time (`knowledge_service.extract_text` -- reuses `recipe_service.extract_pdf_text` for PDFs rather than duplicating pypdf plumbing; `.txt`/`.md` decoded directly; anything else stored but left ungrounded, `has_content: false`, not an upload error). `GET /api/knowledge-files` never returns the full extracted text (`content_excerpt` is a 300-character preview only); `PATCH` toggles `is_active`/edits the description; `DELETE` removes both the DB row and the file from disk.

**Knowledge-file grounding**: `health_service.build_knowledge_context()` concatenates every *active* file's extracted text (truncated to a combined 3000-character budget via `_format_knowledge_excerpts`, each chunk labeled with its filename) and `gather_generation_context()` includes it as `knowledge_context`, injected into the generation prompt as reference material the model should follow where it doesn't conflict with stated dietary restrictions. **Documented simplification**: this is simple concatenation-with-truncation, not retrieval -- fine for a handful of short reference documents (a doctor's guidance sheet, a specific diet plan) but would need real chunking/embedding-based retrieval to scale to a large knowledge base. Noted here for a future pass rather than over-built now.

Frontend (`frontend/src/pages/HealthPage.jsx`, `components/TrendChart.jsx`, `components/KnowledgeFilesPanel.jsx`): household preferences editor, member add/remove list, a per-member metric-logging form (date, weight in lbs, LDL/HDL/total cholesterol, triglycerides, blood pressure, glucose) with a history table (delete per entry), two `TrendChart` sparkline-style panels (weight, LDL) built as plain inline SVG rather than adding a charting library dependency -- the app has stayed dependency-light through five phases and the data volumes here (a handful of log entries) don't warrant one; gracefully shows "not enough data yet" below 2 points instead of erroring. `KnowledgeFilesPanel` (upload/list/activate-toggle/delete) is self-contained like Phase 5's `GroceryListPanel`. Nav/routing extended with `/health`. `theme.css` gained matching styles for member rows, trend charts, and the knowledge file list.

**Verification**: unit tests for the pure functions (`compute_bmi`, `bmi_category`, `compute_metric_trend` against within-window/outside-window/fallback-to-earliest/insufficient-data cases, `format_member_health_line`, `_format_knowledge_excerpts` truncation) run directly against the service modules; a live curl sequence against a fresh local backend covering preferences update, member CRUD, metric logging with server-computed BMI verified against a hand-calculated expected value, the trends endpoint, knowledge-file upload/list/deactivate/delete (including confirming the file is actually removed from disk), and 404s; **directly verified the generation prompt itself contains the injected health and knowledge grounding text** (not just that the context dict was built) by calling `gather_generation_context` + `build_generation_prompt` against the live test DB and asserting the member's name/BMI/trend and the uploaded file's content appear in the resulting prompt string; frontend `npm run build` succeeds cleanly; a full live Vite-dev-server + real-backend pass exercised preferences, member creation, metric logging, and knowledge-file upload/list through the actual browser-facing proxy path. ## Phase 7 notes: persistent chat system

Backend (`backend/app/routers/chat.py`, `app/services/chat_service.py`, `app/schemas/chat.py`):

**Schema** (migration `5c07836d9339`): `ChatMessage` (already existed from the Phase 1 schema, unused until now) gained `actions` (JSON, nullable) -- structured action proposals attached to an assistant message, so history replay after a page reload can still show actionable cards, not just the reply text. Always null on user messages.

**Sessions are implicit, not a separate table**: a session is just a distinct `session_id` value already present in `chat_messages`. `GET /api/chat/sessions` derives a summary (message count, last-message time, a truncated preview) with a `GROUP BY`, ordered most-recent-first; `DELETE /api/chat/sessions/{id}` deletes all rows for that id. The frontend generates its own `session_id` (`crypto.randomUUID()`, persisted in `localStorage`) rather than calling a `POST /sessions` endpoint -- a session only "exists" server-side once its first message is sent.

**Context grounding**: `chat_service.build_chat_context()` pulls the currently-relevant meal plan (the `active`-status one if there is one, else the most recently created plan at all, so chat is still useful before a plan is manually activated) and up to 80 inventory items, then `build_chat_system_prompt()` appends a formatted block -- household size/dietary restrictions, meal-plan entries with their real `entry_id`s and status, inventory items with their real `id`s -- to the `main_chef` system prompt. The prompt explicitly instructs the model to never invent an `entry_id`/`meal_plan_id`/ingredient reference not listed, asking a clarifying question instead of guessing. Verified directly (same technique used in Phase 6): called `build_chat_context` + `build_chat_system_prompt` against a live test DB and asserted the actual inventory ids, entry id, household size, and entry status appear in the literal resulting prompt string.

**Actions are proposals only, never executed server-side**: `chat_service.parse_chat_response()` defensively extracts `{"reply", "actions"}` from the model's output (reusing the same `_extract_json_object` helper recipe import and meal-plan generation use), coercing each action against `ALLOWED_ACTION_TYPES` (`inventory_deduct`, `inventory_update`, `inventory_add`, `meal_plan_confirm_entry`, `meal_plan_skip_entry`) and dropping anything malformed. Unlike the structured-extraction tasks in earlier phases, chat is free-form conversation and far more likely to break a "JSON-only" instruction -- if no JSON object with a `reply` key is found at all, the raw text is used as the reply verbatim with an empty actions list, rather than showing the user nothing. `routers/chat.py` persists the proposal alongside the assistant message but does not act on it; the frontend calls the same pre-existing endpoint the rest of the app already uses for that change when the user clicks confirm (`POST /api/inventory/deduct`, `/api/inventory/update-by-name`, `POST /api/inventory`, or the Phase 5 `/api/meal-plans/{id}/entries/{id}/confirm`/`/skip`) -- deliberately avoiding a second, duplicate action-execution layer. This also means a hallucinated id isn't specially validated in chat code at all; it just 404s from the real endpoint like any other bad id would, verified live by proposing a confirm action against a nonexistent `meal_plan_id`/`entry_id` and confirming the real endpoint rejects it.

**New small endpoints, not new machinery**: name-based `POST /api/inventory/deduct` and `POST /api/inventory/update-by-name` were added to `routers/inventory.py` (static paths, correctly ordered before `/{item_id}`) because chat needs to resolve a natural-language ingredient name to a row without knowing its id -- the underlying matching logic (`inventory_service.find_by_name`, extracted from what was inlined in `deduct_by_name`) already existed and is now shared by both `deduct_by_name` and the new `update_by_name`. No new endpoints were needed for meal-plan actions since `/confirm`/`/skip` already existed from Phase 5.

Frontend (`frontend/src/components/ChatWidget.jsx`): mounted once in `App.jsx` at the app-shell level, outside `<Routes>`, so it stays alive (history, in-flight sends, open/closed state) across route navigation -- the core requirement for "chat keeps running/visible in the background while navigating the app." A floating toggle button docked bottom-right expands into a panel with message history, action cards (each rendering the model's `description` with its own Confirm button that calls the corresponding real endpoint per the mapping above, tracking pending/done/error state per action so a card can't be double-applied), and a text input. History is fetched once on mount from `GET /api/chat/messages?session_id=`, so a full page reload restores the conversation (not just in-memory persistence across navigation). `theme.css` gained a `.chat-widget*` block reusing existing design tokens and the `.chat-msg`/`.card`/`.btn` classes already established by Phase 4.1's ephemeral recipe chat, rather than inventing a parallel style vocabulary.

**Verification**: unit tests for `parse_chat_response` (strict JSON, malformed-fallback-to-raw-text) and `_coerce_action` (all five action types, invalid type, missing required field) run directly against the service module; a live curl sequence against a fresh local backend (real Alembic migration + seed, mocked `ollama_client.chat` returning different canned responses keyed off trigger substrings in the message text) covering a plain reply with no actions, an `inventory_deduct` proposal, an `inventory_update` proposal, a `meal_plan_confirm_entry` proposal against real ids, the malformed-JSON-falls-back-to-raw-text case, a deliberately hallucinated meal-plan id, full history round-trip (including the `actions` JSON field surviving persistence), session listing/multi-session/deletion, and the empty-message 400 case; then confirming each proposed action for real through its actual endpoint (`/api/inventory/deduct`, `/api/inventory/update-by-name`, `/api/meal-plans/{id}/entries/{id}/confirm`) and hand-verifying the resulting inventory/meal-plan state, plus confirming the hallucinated-id action correctly 404s against the real endpoint instead of silently succeeding; directly inspected the generated system prompt text (same technique as Phase 6) to confirm real inventory/meal-plan ids are actually injected, not just present in an intermediate context dict. Full design rationale, including what was deliberately adapted or not ported and why, is written up in `backend/app/services/knowledge_service.py`'s module docstring rather than duplicated here -- summary follows.

**Schema** (migration `5ee4a7ad013b`): new `KnowledgeChunk` table (`knowledge_file_id` FK with cascade-delete via the ORM relationship, `chunk_index`, `text`, `vector` as a JSON `list[float]` -- no vector DB needed at this corpus size, matching Fiduciary's validated approach). `KnowledgeFile` gained `indexed_embed_model` (nullable `String`) -- compared against the current `ollama_embed_model` setting to decide whether a file needs (re)indexing, covering both "never indexed" (null) and "the configured embed model changed" in one check.

## Recipe variants: committing an AI-modified recipe (feature, completed 2026-07-31)

Added in response to a direct follow-up question, not a pre-queued backlog item: the author asked whether an AI-modified recipe (e.g. "take this imported recipe and make it gluten-free") could ever be *saved*, since chat modifications were previously always ephemeral. Confirmed via code inspection that this capability did not exist (`RecipeChatResponse` only carried `reply`; persistent chat's `ALLOWED_ACTION_TYPES` had no recipe-modification type) before building it. The author wanted both chat surfaces able to propose edits, and asked for a "version or variant system" if feasible, with an explicit fallback to safer overwrite-only behavior if not -- safety (never accidentally serving a recipe that's drifted out of sync with dietary needs) was the stated top priority.

**Schema** (migration `349c7fd3ed4c`): `Recipe` gained `parent_recipe_id` (nullable self-referential FK, `sa.ForeignKey("recipes.id")`, added via `op.batch_alter_table` since SQLite can't `ALTER TABLE` a raw FK constraint) and `variant_label` (nullable `String(100)`, e.g. "Gluten-Free"). A variant is deliberately just a normal, independent `Recipe` row that happens to point at the recipe it was derived from -- not a diff/patch/version-history entry -- the simplest structure that satisfies "keep the original safe from accidental modification" without over-building something not asked for. No cascade delete on the FK (same accepted SQLite-doesn't-enforce-FK-by-default tradeoff as `HealthMetricEntry.household_member_id` from Phase 6): a variant should survive its parent being deleted, since by that point it's a real independent recipe, not a dependent patch. ORM relationship: `Recipe.variants` (children) / `Recipe.parent_recipe` (backref, `remote_side="Recipe.id"`), verified bidirectionally against a live test DB.

**Recipe-scoped chat can now propose edits** (`recipe_service.RECIPE_MODIFY_INSTRUCTIONS`, `parse_recipe_chat_response`): the existing read-only "Ask the Chef" chat (Phase 4.1) is extended, not replaced -- every turn can still be a plain answer, but a message like "make this gluten-free" now gets a `proposed_recipe` (the entire recipe as it should look after the edit, same shape as recipe import, coerced through the existing shared `coerce_recipe_fields()`) and a suggested `variant_label`. `RecipeChatResponse` gained both fields. Same preview-then-confirm discipline as every other AI-structured-output feature in this app -- nothing is saved by chat code itself, only proposed.

**Persistent chat gained `recipe_update_proposal`**, initially variant-ONLY -- it always created a new `Recipe` row via `parent_recipe_id`/`variant_label`, with no in-place overwrite path, since the widget's confirm is a single click with no review form the way the recipe-scoped chat's `RecipeForm` step is. **Extended same day** after the author asked directly whether an overwrite path was available from chat at all, for either the original recipe or a specific variant. Answer: the recipe-scoped chat already supported this implicitly (it's scoped to whatever recipe/variant page the user is viewing, and already offered an overwrite choice there), but the persistent widget didn't. Added a `"mode": "variant"|"overwrite"` field to the action (default `"variant"`, so existing behavior is unchanged unless the user's phrasing clearly asks to update/replace/overwrite the existing recipe rather than save a copy -- `CHAT_CONTEXT_TEMPLATE` spells out the distinguishing phrases and instructs defaulting to `"variant"` when ambiguous). An unrecognized/missing `mode` value from the model falls back to `"variant"`, the safer default, rather than being trusted as-is (`chat_service._coerce_action`). `ChatWidget.jsx`'s `executeAction` branches on `mode` (POST a new recipe with `parent_recipe_id` set, vs. PATCH the target recipe directly), and `ActionCard` requires an extra native `window.confirm()` specifically for `"overwrite"` mode before calling through -- a deliberate speed bump matching the app's existing convention of a browser confirm for destructive actions (e.g. recipe delete), since this is the one action type in the persistent chat that can silently replace a recipe's content with no review step first. `chat_service.build_chat_context()` also gained a lightweight `recipe_catalog` (id, title only) so the model can reference an existing recipe by a real id; `CHAT_CONTEXT_TEMPLATE` explicitly forbids inventing a `target_recipe_id` not in that list, same discipline as the existing `entry_id`/`meal_plan_id` guard from Phase 7.

**New endpoint**: `GET /api/recipes/{id}/variants` lists a recipe's children. `_to_read()` (in `routers/recipes.py`) now populates `parent_recipe_title` (via `recipe.parent_recipe.title if recipe.parent_recipe else None`) and `variant_count` (via `len(recipe.variants)`) on every `RecipeRead`, so the detail page can show "Variant of X" / a variants list without extra round-trips for the common case.

**Frontend**: `RecipeForm.jsx` gained an optional `submitLabel` prop (default unchanged, "Save recipe") so the same shared form can be reused for non-edit submit flows with different button text. `RecipeChat.jsx` shows a review card when a turn's response includes `proposed_recipe`: a radio choice between "Save as a new variant" (default, with an editable label field pre-filled from the AI's suggestion) and "Update this recipe (overwrite)", reusing `RecipeForm` pre-filled with the proposal; saving as a variant POSTs to `/api/recipes` with `parent_recipe_id`/`variant_label` set and navigates to the new recipe, saving as overwrite PATCHes the current recipe and reloads it in place. The proposal is deliberately cleared (not accumulated) whenever a chat turn's reply isn't itself another proposal, since a fresh question implies the user has moved on from reviewing the pending one -- nothing is lost since it was only ever a preview. `RecipeDetailPage.jsx` shows a "Variant of [parent]" link when `parent_recipe_id` is set, a variant-label tag next to the title, and a "Variants" list (fetched from the new endpoint) when `variant_count > 0`. `ChatWidget.jsx`'s `executeAction()` gained a `recipe_update_proposal` case that branches on `action.mode` (POST a new variant, or PATCH the target directly for `"overwrite"`, guarded by the `window.confirm()` described above); its confirmed-action card labels itself "Recipe — new variant" or "Recipe — overwrite existing" and links to either "View saved variant" or "View updated recipe".

**Verification**: backend `py_compile` clean across all touched modules; the migration re-applied cleanly through the full chain against a fresh test DB (`PRAGMA table_info`/`PRAGMA foreign_key_list` confirmed the new column/constraint). End-to-end verification used a live FastAPI `TestClient` against a fresh seeded DB with `ollama_client.chat` monkeypatched (no live Ollama reaches the sandbox, same constraint as every prior phase) to return canned structured responses, covering: the recipe-scoped chat proposing a gluten-free ingredient swap and the resulting `proposed_recipe`/`variant_label` round-tripping correctly; saving that proposal as a new variant and confirming the parent's `variant_count` and `GET .../variants` both reflect it and `parent_recipe_title` resolves correctly on the child; the persistent chat's `recipe_update_proposal` action in both modes, including confirming the recipe catalog appears in the literal generated system prompt text (same "inspect the real prompt, not just the context dict" technique used since Phase 6/7), that a deliberately hallucinated extra action type in the same response is silently dropped, and that an unrecognized/missing `mode` value coerces to the safer `"variant"` default rather than being trusted as-is; simulating `ChatWidget.jsx`'s exact `executeAction` calls for both the POST-a-variant and PATCH-to-overwrite paths and confirming each lands correctly (the overwrite case confirmed against a recipe that already had two prior variants, verifying its own `variant_count`/`parent_recipe_id` were unaffected by the content update); and the recipe-scoped chat's "overwrite in place" PATCH path. **B1.2 -- summation, with an honest three-way provenance label.** `Recipe` gained `nutrition_provenance` (migration `8f2c4b6a1d9e`, nullable `String(20)`: `computed` / `partial` / `ai_estimated` / `None` for a legacy never-touched row). New pure functions in `food_data_service.py`:

- `compute_ingredient_grams(ingredient)` -- converts one ingredient's `quantity`+`unit` to grams via `unit_conversion_service.convert(quantity, unit, "g")`. Returns `None` for no stated quantity, a count-based unit ("2 eggs"), or a volume-based unit ("1 cup") -- the last case is a real, documented limitation: nothing in this codebase sources a per-ingredient density yet (USDA FDC does publish portion/gram-weight data that could eventually fill this gap, `resolve_and_cache_ingredient` just doesn't parse it), so a recipe with only volume-unit ingredients can resolve 100% against USDA/OFF and still never reach `"computed"`. This is the same gap B5.3/B10.5's notes already flagged for the weight-mode toggle -- one missing piece blocks both.
- `compute_recipe_nutrition(recipe)` -- sums each ingredient's cached `nutrition_per_100g` scaled to its actual gram weight, divides by `default_servings` (falling back to 1 rather than dividing by zero), and returns `(nutrition_dict, provenance)`. Ingredients with no stated quantity (e.g. "salt to taste") are excluded from both the sum and the completeness check -- they're not a resolution failure, there's just nothing to weigh. `"ai_estimated"` is returned with the recipe's **existing** nutrition dict completely unchanged (never blanked, never overwritten with a fabricated zero-ingredient total) whenever nothing contributed real data; `"computed"` only when every quantified ingredient contributed; `"partial"` otherwise, with the dict being an honest sum over an incomplete ingredient list (documented in the UI, see below, as a likely undercount, not a final number).

**New endpoint** `POST /api/recipes/{id}/compute-nutrition` (`force` query param, same semantics as the existing `/resolve-nutrition`): resolves any never-attempted ingredient first (skips already-`"unresolved"` ones unless `force=True`, so this doesn't silently start retrying every failed lookup's network call on every click), then calls `compute_recipe_nutrition` and persists -- `Recipe.nutrition` is only overwritten when the result isn't `"ai_estimated"`, so an existing AI guess is preserved (just correctly labeled) rather than erased when resolution finds nothing to compute from. `RecipeRead` gained `nutrition_provenance` (output-only, like `RecipeIngredientRead.resolution_source` -- never accepted from `RecipeCreate`/`RecipeUpdate`, so a client can't just assert `"computed"`).

**Provenance on the normal create/update paths, and a bug avoided, not just fixed.** `create_recipe` (router) and `recipe_service.create_recipe_from_parsed` (used by meal-plan generation's `new_recipe`) both set `nutrition_provenance="ai_estimated"` whenever a non-empty nutrition dict comes in -- an AI guess and a manually-typed value share the same "not verified against a food database" bucket. `update_recipe`'s PATCH handler only resets provenance back to `"ai_estimated"` when the incoming `nutrition` dict actually **differs** from what's stored -- caught during design, not by a failing test: `RecipeForm.jsx` always resends whatever nutrition fields it loaded (see the frontend section below), so a same-value resend on an unrelated edit (retitling, toggling staple) would otherwise silently demote a `"computed"` recipe back to `"ai_estimated"` on every save with no nutrition change at all. Verified live (see below) that an unchanged-nutrition PATCH leaves `"partial"`/`"computed"` alone while a changed one correctly resets to `"ai_estimated"`.

**Frontend.** `RecipeForm.jsx`'s nutrition fieldset previously hardcoded exactly 4 of the (now 9) possible keys -- a real, pre-existing data-loss bug found during the B1.2/B1.3 code survey: editing any recipe that had `fiber_g`/`sodium_mg`/`cholesterol_mg`/etc. (from the 7-key import prompt) silently dropped those keys on save, since the submit builder only ever wrote back the 4 it knew about. Replaced the four hardcoded fields with a `NUTRIENT_FIELDS` config array driving state init/hydration/submit-building/JSX rendering from one list, so the three can't drift apart again the way the original 4-vs-7-vs-9 split happened in the first place. Added a hint above the fieldset warning the user that editing-and-saving a `"computed"`/`"partial"` recipe's nutrition here will mark it back to `"ai_estimated"` (true, and now the correct behavior per the paragraph above -- editing IS a real change). `RecipeDetailPage.jsx` gained a `PROVENANCE_INFO`-driven badge above the nutrition list (green "Computed from ingredient data" / amber "Partially computed..." / muted "AI estimate -- not verified..."), a `NUTRIENT_LABELS` map for friendlier display text (falls back to the raw key for anything unrecognized), and a "Compute from ingredients" button wired to the new endpoint. `theme.css` gained `.provenance-badge`/`.provenance-computed`/`.provenance-partial`/`.provenance-estimated` (reusing the existing secondary/accent/text-muted tokens, same traffic-light convention as the Settings page's `.status-dot` and the Health page's trend-chart coloring) and `.nutrition-field-grid` (a `repeat(auto-fill, minmax(140px, 1fr))` grid for the now-9-field fieldset -- deliberately given its own class rather than reusing `.form-row`, since `.item-form .form-row`'s existing `display: flex` rule has higher specificity than a bare `.nutrition-field-grid` class and would have silently overridden the grid layout).

## Fix: BACKEND_PORT changeable without a frontend rebuild (2026-07-31)

Author-reported: tried to run the stack and port `8095` was already in use on their host. Changing `BACKEND_PORT` in `.env` alone didn't fix it -- the production frontend build talked to the backend at a hardcoded `8095` baked into `src/api.js` at build time (documented as a known simplification since Phase 3, and explicitly called out again in README's "Known limitation" section), so the two ports drifted apart the moment `BACKEND_PORT` changed. Fixing this properly (not just telling the author to edit `api.js` and rebuild) needed a way for the already-built static bundle to learn the current `BACKEND_PORT` at container *start*, not build time.

**Runtime-config injection, not a build-time constant.** Added `frontend/docker-entrypoint.sh` (mirrors the backend's own `docker-entrypoint.sh` pattern) which runs on every container start and writes `dist/config.js` containing `window.__CHEF_CONFIG__ = { backendPort: "<current BACKEND_PORT>" }` -- `BACKEND_PORT` is already present in the frontend container's environment via docker-compose's existing `env_file: .env`, no compose change needed. `frontend/Dockerfile` copies the script, `chmod +x`s it, and sets it as `ENTRYPOINT` (CMD unchanged: `serve -s dist -l 5173`). `index.html` loads `/config.js` via a plain classic `<script>` tag placed before the module-type app bundle script -- classic parser-blocking scripts always execute before deferred/module scripts regardless of final tag order in the document (module scripts are implicitly deferred per the HTML spec), which matters here because Vite's build always relocates the bundled module script into `<head>`, ahead of where `/config.js` sits in `<body>` -- confirmed the execution-order guarantee holds anyway by building and inspecting the actual output. `src/api.js`'s `BACKEND_PORT` constant now reads `window.__CHEF_CONFIG__?.backendPort || 8095` instead of a literal `8095`.

**A real placeholder file, not just an entrypoint-only fix.** First pass left `/config.js` served by nothing in `npm run dev` (no `dist/`, no entrypoint script running) -- Vite's dev server responded to the unmatched `/config.js` request with its SPA-fallback `index.html` (200, not 404), which the browser then tried to execute as JavaScript and threw a console error on (`<!doctype html>` isn't valid JS). Caught by actually curling `/config.js` against a live dev server rather than assuming a 404, not by inspection. Fixed by adding `frontend/public/config.js` (a real static file Vite serves directly in dev, and copies verbatim into `dist/` at build time) with the same default-8095 content -- so dev mode gets a real, harmless, valid script, and a production build's `dist/config.js` always starts from a valid file even before the entrypoint overwrites it with the real port at container start.

**Dev-without-Docker proxy target, too.** `vite.config.js`'s dev-server proxy (`/api`, `/health`) previously hardcoded `http://localhost:8095` as its fallback target (with `VITE_BACKEND_URL` as the only override). Now falls back to `http://localhost:${BACKEND_PORT}` (read via `loadEnv`, so a `.env`/`.env.local` in `frontend/` or a shell-exported `BACKEND_PORT` both work) before falling further back to the `8095` literal -- consistent with the same env var name used everywhere else in this project for this exact purpose, rather than introducing a second one. `VITE_BACKEND_URL` still takes precedence when set, for the different-host/scheme case that isn't just a port.

**README** updated: the "Known limitation" section no longer says changing `BACKEND_PORT` requires a frontend rebuild (it doesn't, anymore) and now states the actual fix path (change `.env`, `docker compose up`, no `--build`). `.env.example`'s `BACKEND_PORT`/`FRONTEND_PORT` comment expanded to say the same.

**Verification.** `sh -n` syntax-checked the new entrypoint script; ran it standalone against a scratch `dist/` with both a custom `BACKEND_PORT` and no env var set at all, confirming the generated `config.js` content in both cases. Built the frontend from a `/tmp` scratch copy (per the standing FUSE-mount note) and confirmed: `dist/index.html` retains the `/config.js` script tag in the right relative position; `dist/config.js` exists post-build with the placeholder content (copied from `public/`); running the entrypoint script against that same `dist/` afterward correctly overwrites it with a custom port (`9500` in testing); the built JS bundle's minified output actually references `window.__CHEF_CONFIG__` (grepped for the literal string) rather than having it constant-folded away. Served the built `dist/` for real with a plain HTTP server and curled both `index.html` and `config.js` to confirm the exact bytes a browser would receive. Ran a live Vite dev server against a live backend and curled `/config.js` before and after adding `public/config.js`, catching the SPA-fallback issue described above for real rather than assuming dev mode was fine.

## B3.1/B3.2 notes: allergen/restriction model, deterministic check, cross-contact flagging (2026-07-31)

Picked by the author over B1.4/Walmart-import/other options as the next area to tackle, flagged in the backlog as a genuine safety gap (not a nicety) given the stated celiac-friendly requirement. Dietary restrictions were previously free-text JSON (`HouseholdPreferences.dietary_restrictions`) interpreted only by the LLM per prompt -- nothing structurally prevented a generated plan or imported recipe from actually containing gluten if the model missed it. This adds a second, independent, deterministic layer that never trusts the model's own judgment about what it put in a recipe.

**New structured field, kept separate from the existing free-text one.** `HouseholdPreferences.restricted_allergens` (JSON list of fixed enum keys) and `.gluten_observance_level` (nullable string enum) are new columns (migration `c3d8a1f5b7e2`), deliberately not folded into the existing `dietary_restrictions` list -- that field is LLM-interpreted prose ("low sodium", "reduce cholesterol") and conflating it with a field that drives a hard code-level safety check would blur what each one actually guarantees. Restrictions stay household-level, matching every other preference in the data model; there's no per-member dietary concept anywhere in the schema today, and introducing one wasn't asked for.

**`app/services/allergen_service.py` -- the deterministic check itself.** `ALLERGEN_CHOICES` is a 10-entry taxonomy: the nine FDA/FALCPA-and-FASTER-Act major allergens (milk, eggs, fish, crustacean shellfish, tree nuts, peanuts, wheat, soybeans, sesame) plus "gluten" as its own tenth entry, since gluten (wheat + barley + rye + related grains) is broader than "wheat" alone and is the actually-relevant category for celiac disease. Each allergen maps to a keyword list (`ALLERGEN_KEYWORDS`); `find_allergen_matches()` regex-matches every keyword against every ingredient name with `\b` word-boundary anchoring (so "eggplant" doesn't false-positive on "egg") and returns every hit, not just the first, via `finditer` (a real bug caught in testing: "barley malt syrup" checked against "gluten" only reported "barley" with a naive `.search()`, missing "malt"). A `"-free"` negation pass (`_is_negated`) suppresses a match when the ingredient name itself declares the allergen absent ("gluten-free flour", "dairy-free wheat cracker" only flags wheat) -- the negation regex needed its own `\b` fix after a subtle bug where "nut-free" matched as a bare substring inside "peanut-free", incorrectly suppressing an unrelated, legitimate tree_nuts hit on "almond" in the same ingredient string.

**B3.2's cross-contact layer** is `find_cross_contact_matches()`: only fires when gluten is actually restricted AND the household's `gluten_observance_level` is `strict_no_cross_contact` (the other two levels -- `flexible`, `strict_gluten_only` -- don't care about cross-contact by definition), and matches a small `GLUTEN_CROSS_CONTACT_KEYWORDS` list (oats/oat/oatmeal/oat flour/oat milk/oat bran -- the single most common real-world cross-contact risk for celiac diets, since oats aren't gluten-containing but are very commonly processed on shared wheat/barley/rye equipment). Cross-contact matches never set `RestrictionCheckResult.has_conflict` on their own -- they're informational, not blocking, since "may share equipment" is a much softer signal than "contains the allergen."

**Wired into all three points the backlog named.** Import (`RecipeImportResponse.restriction_warnings`/`.cross_contact_warnings`, computed against the parsed ingredients before the recipe is ever saved), every recipe read (`RecipeRead` gains the same two fields, computed fresh on every `GET` rather than cached/persisted -- unlike nutrition resolution, this is a cheap string-match with no network call, and restrictions can change at any time, so a stale cached warning would be actively misleading), meal-plan generation preview (`meal_plan_service.attach_restriction_warnings()` runs against either the AI-proposed new recipe's ingredients or the matched catalog recipe's, informational only since nothing is saved yet), and meal-plan entry confirm (`POST /meal-plans/{plan_id}/entries/{entry_id}/confirm` now checks the actual recipe's ingredients against current household restrictions -- a plan can sit for days before a meal is actually made, during which restrictions could change, so generation-time warnings alone aren't enough). Confirm has real teeth: a hard allergen match returns **409** with the match details unless the request body sets `acknowledge_restriction_conflict: true`, at which point it proceeds and deducts inventory as normal. This is a deliberate, discussed trade-off -- block by default (a silent confirm on a conflicting meal is the failure mode that actually matters for a celiac household) while still leaving a human able to say "I know, do it anyway" for a false positive or an accepted one-off exception. Cross-contact warnings never block confirm on their own, matching their informational-only status everywhere else.

**Frontend.** `RestrictionWarnings.jsx` is a small shared component (red `.restriction-warning` banner for hard matches, amber `.cross-contact-warning` for the softer oats-type signal, matching the existing provenance-badge severity convention) reused in four places: `RecipeDetailPage.jsx` (below the description), `RecipesPage.jsx`'s import-review card (new `importWarnings` state alongside `importPreview`, since `RecipeImportResponse` carries the warnings at the top level, not nested under `.recipe`), `MealPlanPage.jsx`'s generation-preview entries (one banner per previewed slot), and `MealPlanEntryRow.jsx`'s confirm flow. The confirm flow needed one supporting change: `api.js`'s generic error handler previously stringified any non-string `detail` object into `[object Object]`, which would have made the 409's actual match data unreachable by any caller -- fixed by attaching the parsed `.status`/`.detail` onto the thrown `Error` alongside the existing stringified `.message`, a general fix any future structured-error endpoint can also use, not an allergen-specific hack. `MealPlanEntryRow`'s "We made this" button now catches a 409, renders the conflict via `RestrictionWarnings`, and offers "Confirm anyway" (resends with `acknowledge_restriction_conflict: true`) or "Cancel". `HealthPage.jsx`'s household-preferences form gained a checkbox grid (fetched from `GET /household/allergen-options`, a new tiny endpoint exposing `allergen_service.ALLERGEN_CHOICES`/`OBSERVANCE_LEVELS` so frontend and backend can't drift apart) and a gluten-observance-level `<select>` that only appears once gluten is checked.

**Deliberately not done.** No NLP/synonym expansion or compound-ingredient decomposition ("may contain traces of" disclosure text isn't parsed, "enriched flour" isn't expanded to name wheat unless "flour" is itself a keyword, which it is) -- this stays a keyword/regex system, consistent with the project's "never let the LLM invent/guess, but also don't pretend a deterministic keyword match is smarter than it is" discipline; documented as a known limitation in the module docstring. No per-member restrictions (see above). No recall-awareness (that's B3.3, a separate backlog item).

**Verification.** 25 new unit tests (`test_allergen_service.py`; 93 total in the repo, all passing) covering basic matching, case-insensitivity, multi-allergen/multi-ingredient combos, the gluten-superset behavior, word-boundary compound-word avoidance, unknown-key handling, every negation case (including the two regression-fixing cases above), cross-contact gating on both conditions independently, `check_ingredients`' combined-category behavior, `to_dict()` shape, the DB-backed `check_household_restrictions()` wrapper (no-preferences-row, persisted-preferences, and empty-allergen-list cases), and taxonomy self-consistency. Live end-to-end pass against a real local uvicorn instance covered every wiring point: `PATCH /household/preferences` persisting `restricted_allergens`/`gluten_observance_level` and rejecting an unknown allergen key with 422; creating a recipe with "wheat flour" (restricted), "rolled oats" (cross-contact only), and "gluten-free vanilla extract" (correctly NOT flagged, confirming the negation logic) and confirming `GET /recipes/{id}` returns exactly the expected `restriction_warnings`/`cross_contact_warnings`; creating a meal-plan entry against that recipe and confirming `POST .../confirm` returns 409 with the full match payload, then succeeds and sets `is_confirmed: true` once resent with `acknowledge_restriction_conflict: true`. Frontend: `npm run build` succeeds cleanly (built from a `/tmp` scratch copy per the standing FUSE-mount note) with no transform errors across all five touched/new components. **Not independently re-verified this pass**: the recipe-import preview's warnings and the meal-plan-generation preview's warnings were verified by code inspection and the shared unit-test coverage of the underlying `allergen_service` functions they call, not by a live curl through those two specific endpoints (import needs a live Ollama the sandbox can't reach; generation likewise) -- same standing limitation as every prior AI-surface feature in this project. ## Capstone research: best-in-class landscape (2026-07-31)

Competitive/market research pass done *before* looking at Chef's own code, deliberately, so the findings would not be anchored on what already exists. This section records what the field looks like; the gap items it produced live in the Backlog section above. Sources are listed at the end of this section.

### What the incumbent meal planners are each good at

| Tool | The thing it does better than everyone else |
|---|---|
| Paprika | Recipe capture and organization; excellent web clipper, one-time purchase, no subscription. Deliberately not smart -- no AI, no pantry awareness, no plan generation |
| Mealime | Speed and zero setup overhead; short ingredient lists, fast grocery list, ~7M users, genuinely usable free tier. Dinners only. Pro tier adds a "Meal Prep Day" batch-cooking mode |
| Eat This Much | Automated macro/calorie-target-driven generation; merges cook events so leftovers reduce stove time. Thin on variety and inspiration |
| Plan to Eat | Calendar planning and leftover scheduling as first-class concepts; scale servings, reschedule, track frozen meals |
| Samsung Food (ex-Whisk) | AI recipe personalization -- convert a recipe to vegan, rebalance it nutritionally, rewrite it around in-stock ingredients, adjust cook time or skill level. Vision AI calorie estimation from photos (Galaxy devices only). Pantry management exists but is basic and paywalled |
| Tandoor (self-hosted) | The most feature-dense open-source option: barcode scanning into OpenFoodFacts, supermarket aisle mapping, meal cost calculation, URL import across 500+ sites |
| Mealie (self-hosted) | Polish and family usability; clean Docker deployment, strong URL import, good UI |
| Grocy (self-hosted) | Whole-household inventory discipline -- pantry stock, consumption tracking, chores, equipment -- with recipes as one module among several |

Chef's intended position sits between Tandoor's data richness and Eat This Much's automation, with a local LLM and health-metric feedback loop neither of them has. The gaps worth closing are mostly Tandoor's data-layer features (barcode, aisles, cost) and Plan to Eat's / Mealime Pro's planning mechanics (leftovers, prep day), not the AI layer where Chef is already ahead.

### Nutrition data services

- **USDA FoodData Central** -- free, government-backed, ~300K+ items, full nutrient profiles, API key required. No barcode lookup, weak branded coverage. The correct authoritative base layer.
- **Open Food Facts** -- free, open, crowd-sourced, ~2.5M+ packaged products, barcode-native. Best complement to USDA for branded/packaged goods, and the right choice for an app shipped to self-hosters.
- **Nutritionix / Edamam / Spoonacular / FatSecret** -- aggregate USDA plus branded and restaurant data, with genuinely better NLP (Edamam's is purpose-built for user-submitted recipe text) and restaurant-menu coverage (Nutritionix). All paid past a low free tier; Edamam scales to ~$999/mo and Nutritionix enterprise starts around $1,850/mo. Rejected as a dependency for this repo -- fine as an optional user-configured integration, wrong as a requirement for anyone cloning it.
- **USDA FoodKeeper** -- machine-readable feed of storage/shelf-life guidance for 500+ foods, and the source app now surfaces FSIS/FDA recall notifications.
- **USDA FSIS Recall API and openFDA food enforcement API** -- both free and public; openFDA covers 2004-present, updated weekly.

### Nutrition standards worth encoding

- **DRIs** (EAR, RDA, AI, UL) from the National Academies are the reference values the Dietary Guidelines are built on -- the right basis for per-member daily targets from age/sex/height/weight/activity.
- **HEI-2020** -- 0-100 diet quality score, 13 components (9 adequacy, 4 moderation), scored against the Dietary Guidelines. US population average is 58/100. Computable, published methodology, gives an objective plan-quality number.
- **Portfolio diet** -- the pattern specifically engineered for LDL reduction (plant sterols, viscous fiber, nuts, soy protein), overlapping with but more targeted than DASH or Mediterranean. Directly relevant to the author's stated goal. DASH additionally targets sodium (1,500-2,300 mg/day) and lowers LDL and triglycerides; Mediterranean lowers LDL while raising HDL.
- **RAG grounding for nutrition advice is an active research area**, and the recurring finding is that LLM systems which do not encode population reference-intake distributions risk producing recommendations without appropriate nutritional constraints. Chef's knowledge/RAG layer is the right shape for this; it just ships empty (see B2.1).

### Celiac and allergen tooling

Fig and Spoonful are the reference implementations. Two capabilities stand out and neither is present in Chef: a user-set **observance level** (must avoid gluten and cross-contamination is not ok / must avoid gluten but cross-contamination is ok / trying to avoid), and **cross-contact flagging** that goes beyond the ingredient list -- e.g. flagging non-certified oats and shared-equipment risk rather than only matching the word "wheat."

### Inventory capture, food waste

The whole category (NoWaste, Your Food, PantryWise, ShelfSmart, Recipy, NourishMate, GroceryTracker Pro, Dietrack) has converged on the same three mechanisms: **barcode scan**, **receipt OCR** (leading implementations claim 95%+ line-item accuracy on standard supermarket receipts, translating SKU codes into full product name/UPC/category), and **photo recognition**. On top of that, universally: color-coded expiry status, expiry-sorted lists, and **notifications ahead of expiry** (commonly 7 days out and on the day). Chef has photo recognition and urgency scoring but neither barcode nor receipt capture, and no notification of any kind.

### Cooking-time UX

Cook mode with the Screen Wake Lock API (user-activated toggle, battery-impact warning), step check-off, inline kitchen converters (cups/grams, F/C, pan size), step timers, and PWA installability with offline access -- this cluster is standard now and Chef has none of it. WCAG 2.1 AA is the accepted benchmark for PWAs; large-type high-contrast rendering matters more than usual for a screen being read across a kitchen with messy hands.

### Recipe interchange

**Schema.org Recipe JSON-LD** is the de facto interchange format -- Google's recommended structured data, published by most recipe sites, and what enables read-aloud/assistant guidance (needs `recipeIngredient` and `recipeInstructions`). Parsing it directly is faster and more accurate than LLM extraction from prose. **Cooklang** is the notable plain-text alternative. Public recipe-scaling APIs exist that handle smart culinary fractions and unit promotion.

### Health data integration

CGM data reached consumers in 2026 -- Withings ingests Abbott Lingo readings via Apple Health / Health Connect and, as of Q1 2026, a direct API. Aggregator APIs (Terra and similar) cover 500+ wearables including CGM data types but are paid and cloud-dependent, which fits a local-first self-hosted app poorly. File-based export import from Apple Health / Google Health Connect is the pragmatic first step.

### Grocery pricing reality check

Kroger publishes a public developer API for its own stores; Walmart publishes no public price API; Instacart pricing is reachable mainly through third-party scraper services. The honest 2026 assessment of AI recipe apps is that they are price-blind unless they hand the cart to a real merchant that returns live pricing. For a self-hosted app distributed to strangers, scraping is not an acceptable dependency -- user-entered or receipt-derived pricing is the deliverable, retailer APIs at most an optional per-user integration.

## Model selection: default Ollama chat/vision models updated (2026-07-31)

The author asked whether Fiduciary's models (they run `qwen3.6:27b` + `bge-m3`) should replace Chef's original defaults (`qwen2.5:14b` chat, `llava:13b` vision), and whether a newer Qwen release than 2.5 should be used at all. Checked Fiduciary's actual code rather than trust the paraphrase (`docs/DEPENDENCIES.md`, `.env.example`, `portfolio-api/llm.py`) -- confirmed it uses `qwen3.6:27b` (dense, tool-calling required for its agentic Strategist) and `bge-m3`, and confirmed it has **no vision model anywhere in its stack** (grepped for vision/image/llava/qwen-vl config, only generic-English-word false positives came back). Chef's `ollama_embed_model` default was already `bge-m3`, matching Fiduciary -- no change needed there.

Web research (Alibaba's own published benchmarks plus several 2026 model-comparison writeups; the specific quality claims below rest on vendor/blog-reported numbers, not independently reproduced) found: `qwen3.6:27b` is a real April-2026 dense-27B release, strong on coding/agentic-tool-use benchmarks (SWE-bench, Terminal-Bench) -- the right fit for Fiduciary's workload, but a poor default for Chef's on this specific hardware. At 17GB it doesn't fit a single 11GB GTX 1080 Ti; Ollama's multi-GPU support (automatic since v0.11.5) would split it across both cards, but tensor-splitting only lets a bigger model fit -- it does not parallelize a single request, so cross-GPU communication over non-NVLink PCIe likely makes generation *slower*, and it would occupy both GPUs per request, defeating the author's own hardware-section intent that the second 1080 Ti stay free for a concurrent second model. `qwen2.5vl:7b`, by contrast, was found to meaningfully outperform LLaVA-family models specifically on structured/document visual content (labels, receipts, charts) -- directly relevant to Chef's vision use cases (inventory photo intake now, receipt OCR B4.2 later) -- while being smaller (6GB vs. 8GB) than `llava:13b`.

**Decision (author-confirmed)**: switched the seeded defaults to **`qwen3.5:9b`** (chat/meal-plan/recipe generation -- a newer Qwen generation than 2.5, 6.6GB, fits one 1080 Ti with headroom, reportedly strong on general knowledge/instruction-following/multimodal benchmarks even against much larger models) and **`qwen2.5vl:7b`** (vision). `qwen3.6:27b` was deliberately NOT made the default -- documented in `settings_service.py`'s new description text as a reasonable upgrade path on beefier/single-larger-GPU hardware, same optional-override pattern Fiduciary itself uses for its own heavier model via `ANALYSIS_MODEL`. The author is removing `qwen2.5:14b` and `llava:13b` from their Ollama instance since they're no longer the target defaults.

**Changed**: `SETTING_SPECS` defaults in `settings_service.py` (chat -> `qwen3.5:9b`, vision -> `qwen2.5vl:7b`, with the reasoning captured in each spec's `description` so it surfaces in the Settings UI itself, not just here), `.env.example`'s optional first-run seed values, and `README.md`'s prerequisites section. These are **defaults for a fresh install only** -- an existing database that already seeded `qwen2.5:14b`/`llava:13b` keeps those values until changed via the Settings page (by design: `seed.py` never overwrites an existing setting).

**Not done, worth a follow-up**: no empirical A/B test of `qwen3.5:9b` vs. the old `qwen2.5:14b` was run against Chef's actual prompts (recipe-import JSON parsing, meal-plan generation) -- the recommendation rests on published general-purpose benchmarks, not Chef-specific verification, and no live Ollama reaches Claude's sandbox to run one. Fiduciary has a `scripts/model_ab.py` pattern worth mirroring here once the author has both models pulled and can run a real comparison.

## Multi-theme support: Fiduciary themes + Catppuccin (2026-08-01)

Author-requested, direct follow-up to noticing Fiduciary has a Settings-page theme section. Asked for that project's themes ported in alongside Chef's existing default palette, plus Catppuccin (catppuccin.com) as its own option; when asked how many of Catppuccin's four "flavors" to include (Latte/Frappé/Macchiato/Mocha), the author chose all four rather than just the flagship Mocha.

**Investigated Fiduciary's actual mechanism before porting anything** (via a research-only subagent, since Fiduciary's frontend turned out to be a single vanilla-JS/HTML file, not React as assumed going in -- the *mechanism* still ported directly, only the JS glue needed adapting). Fiduciary uses plain CSS custom properties overridden via a `data-theme` attribute on `<html>`, with `localStorage`-only persistence and a synchronous pre-hydration apply to avoid a flash of the wrong theme on load. Chef adopts the same `data-theme` mechanism, but with two deliberate departures given the project's own persistence requirement ("content should be persistent across container rebuilds") and existing infrastructure: (1) the real source of truth is a new DB-backed `ui_theme` setting (one new `SettingSpec` entry, no schema change -- `AppSetting` is already a generic key/value table, and `seed.py`/the existing `GET`/`PATCH /system/settings/{key}` endpoints handle it with zero additional code), with `localStorage` kept only as an instant-apply *cache* for the flash-avoidance trick, reconciled against the DB value once the app mounts (`App.jsx`'s new effect); (2) Chef's ~10 color vars (`--color-bg/-surface/-text/-text-muted/-primary/-primary-hover/-secondary/-accent/-danger/-border`) were already the semantic layer with no separate Tier-1-primitives/Tier-2-semantic split the way Fiduciary's `--bg`/`--amber`/etc. needed -- so each theme is one flat `:root[data-theme="key"]` block overriding exactly those 10 vars, nothing renamed. A genuine advantage found along the way: Fiduciary's own overlay/rgba tokens needed manual per-theme restating because raw `rgba(r,g,b,a)` literals don't recompute from a hex var -- Chef never had that problem because every derived tint in `theme.css` already uses `color-mix(in srgb, var(--color-x) N%, transparent)` (established in the B3.1/B3.2 warning banners and B1.2's provenance badges), which resolves `var()` live, so all of those automatically recolor correctly under every new theme with zero extra per-theme work.

**Ported four Fiduciary themes verbatim** (colors copied from `portfolio-api/static/index.html`'s own `:root[data-theme]` blocks, not re-invented): `amber` (Fiduciary's own dark-terminal default -- an additional selectable option here, not Chef's default), `cobalt`, `highcontrast`, and `daylight` (Fiduciary's one light theme, whose color choices in the source file are themselves the product of two rounds of the author's own live contrast feedback per that file's comments -- inherited as-is rather than re-litigated). Fiduciary's `--bd2`/second-border-strength tier and `--dim`/third-text-fade tier have no Chef equivalent (Chef has one `--color-border` and two text tiers, not three) and were dropped rather than added net-new just to preserve every source value.

**Added all four Catppuccin flavors** (`catppuccin-latte/frappe/macchiato/mocha`, hex values from catppuccin.com/palette, fetched live rather than from training-data memory). Catppuccin's own token names (Base/Mantle/Crust/Surface0-2/Text/Subtext0-1/Mauve/Green/Red/Peach/Lavender/etc.) don't map 1:1 onto Chef's semantic vars, so a mapping was chosen and applied identically across all four flavors rather than improvised per-flavor: `bg`=Base, `surface`=Surface0 (Mantle for Latte specifically -- Latte's lightness ramp has nothing brighter than Base to serve as an "elevated card" tone the way Surface0 is lighter-than-Base in the three dark flavors, so Mantle's slightly-darker/warmer tone is the closest available separation), `border`=Surface1, `text`=Text, `text-muted`=Subtext0, `primary`=Mauve (Catppuccin's own most iconic/branding hue -- it's literally the site's `<meta name="theme-color">` value for Mocha), `primary-hover`=Lavender, `secondary`=Green, `danger`=Red, `accent`=Peach (the closest analog to Chef's own default accent's "warm highlight" role). This mapping choice is documented directly in `theme.css`'s comment block, not just here, so a future flavor addition (Catppuccin doesn't currently have a fifth) has a documented convention to follow.

**New files/changes**: `frontend/src/themes.js` (the JS-side registry -- `THEME_OPTIONS` with per-theme swatch-preview colors grouped by family, plus `applyTheme()`/`getCachedTheme()`); `frontend/index.html` gained a small inline, un-deferred `<script>` before `<div id="root">` that reads the cached theme from `localStorage` and sets `data-theme` synchronously, mirroring Fiduciary's own "apply as early as possible" comment; `App.jsx` gained a mount-time effect that fetches `GET /system/settings`, and if the DB's `ui_theme` differs from the cached value (e.g. changed from a different browser/device), reconciles by re-applying and re-caching; `SettingsPage.jsx` gained a new "Appearance" card (swatch-card grid, grouped by family, click-to-apply-and-save) ahead of the existing generic settings list, which now excludes `ui_theme` from its own plain-text-field loop so the field isn't editable two different ways; `theme.css` gained the 8 new `:root[data-theme]` blocks plus `.theme-swatch-*`/`.theme-group-label` picker styles, following the existing `.status-dot`-adjacent-block placement convention.

**Deliberately not done**: no per-theme override of spacing/radius/font-sans -- matching Fiduciary's own explicit design decision that only color primitives are themed, confirmed still appropriate here since nothing in the request asked for structural changes, only color schemes. No validation of the `ui_theme` value against the known-key set on the backend -- consistent with every other `SETTING_SPECS` entry today (none are value-validated, only key-validated via `is_known_key`), so an unrecognized value just falls through to `themes.js`'s own `VALID_KEYS` guard (silently coerces to `"default"`) rather than the API rejecting it; tightening this uniformly across all settings would be a separate, broader change.

**Verification**: `npm run build` succeeds cleanly (built from a `/tmp` scratch copy per the standing FUSE-mount note) with 52 modules transforming without error; grepped the built, minified CSS to confirm all 8 `data-theme` selectors survived minification intact, and confirmed `chefTheme` (the localStorage key) is present in the built `index.html`'s inline script. Live end-to-end pass against a fresh migrated+seeded DB and a real local uvicorn instance: `GET /api/system/settings` returns `ui_theme` with its seeded default of `"default"`, and `PATCH /api/system/settings/ui_theme` with `{"value": "catppuccin-mocha"}` persists and round-trips correctly. **Not independently verified**: actual on-screen appearance of any theme (no browser available) -- same standing limitation as every prior UI-only change in this project (B10.4, B10.6, B3.1/B3.2's frontend). Worth a real visual pass across a few themes (especially confirming the Latte/daylight light themes and the high-contrast theme actually read well, since those are the ones most likely to expose a contrast mistake) before considering this fully done.

## B1.4 notes: daily/weekly nutrient roll-up vs. DRI targets (2026-08-01)

Picked as the next item after the theming work, per the author's "continue with the next item on the list" -- the highest-priority unclaimed item in B1 ("Nutrition data integrity," the backlog's own top-priority group), and one of the four options already on the table when the author picked B3.1/B3.2 instead two sessions ago.

**New `app/services/dri_service.py`** computes each household member's daily nutrient targets from age/sex/height (on `HouseholdMember`)/weight (most recent `HealthMetricEntry`, via a new `get_latest_weight_kg`)/activity_level -- fields that existed since Phase 6 and were, before this, never used for anything beyond BMI and a chart. Every numeric guideline used is sourced and cited inline in the module docstring, checked live rather than assumed from training data (the 2025-2030 Dietary Guidelines for Americans were released January 2026 and are current as of this writing): calories via Mifflin-St Jeor BMR x an activity multiplier; protein at 1.2 g/kg (the low end of the 2025-2030 DGA's revised, debated 1.2-1.6 g/kg range -- chosen over the higher end since the stated household context is sedentary, and over the older 0.8 g/kg RDA since that's now documented as a deficiency-prevention floor rather than current DGA guidance); carbs/fat via the decades-stable IOM AMDR ranges (45-65%/20-35% of calories, midpoints used); saturated fat and added sugars both capped at <10% of calories per DGA (unchanged in the 2025-2030 edition); sodium capped at the DGA's flat 2,300 mg/day; fiber via IOM's age/sex-banded Adequate Intake (38g/30g men under/over 50, 25g/21g women under/over 50); cholesterol at a documented 300mg *reference* value, explicitly flagged as NOT a current official DRI/DGA figure since the DGA has published no specific numeric cholesterol cap since 2015 ("as low as possible") -- chosen because it's a common, defensible clinical reference point directly relevant to the author's own stated LDL-reduction goal. Returns `None` plus a `missing_fields` list (e.g. `["weight"]`) rather than ever guessing a target from incomplete data -- the same "never silently invent a number" discipline as B1.2's provenance tags.

**`meal_plan_service.compute_nutrition_summary(meal_plan)`** sums each non-skipped, recipe-assigned entry's `Recipe.nutrition` (always per-serving, per `food_data_service.compute_recipe_nutrition`) into per-day and week totals. A entry's nutrition is added exactly once regardless of `entry.servings` -- `entry.servings` scales how much gets cooked/deducted from inventory (`compute_grocery_list`), not how much any one person eats, and the per-serving figure already represents one person's portion, which is the right unit for a per-person total. Explicitly documented known simplification: this assumes every household member eats exactly one serving of every planned meal -- there's no per-person meal-attendance or portion tracking anywhere in the schema to do better. Each day also reports `entry_count` vs. `contributing_entry_count` (a recipe that's never had nutrition computed or estimated doesn't silently vanish from the day, nor does it get blended in as a fake zero -- the gap is visible).

**New `GET /api/meal-plans/{plan_id}/nutrition-summary` endpoint** combines the two: per-day/week totals plus every household member's target (or `missing_fields` if incomplete), so a household member missing body data still shows up in the response with an explanation rather than being silently dropped.

**Frontend**: new `NutritionSummaryPanel.jsx` (same self-contained, `planId`/`refreshKey`-driven pattern as `GroceryListPanel.jsx`) added to `MealPlanPage.jsx` between the weekly entry grid and the grocery list -- a table of per-day + week totals across the same 9-key nutrition set used everywhere else in the app (`food_data_service.NUTRITION_KEYS`), a per-member target list, and a simple "week calories as % of 7-day target" figure per member for a quick at-a-glance read without requiring the user to do the day-to-week-to-percentage math themselves.

**Deliberately not done**: no per-member intake tracking (the household-wide, one-serving-per-meal assumption above is a real, stated limitation, not an oversight -- building real per-person attendance/portions would be a materially bigger schema change with no existing UI concept to hang it on); no visual warning/coloring when a week's totals exceed a cap (sodium, saturated fat, added sugars) -- the raw numbers are shown side by side with the target and left for the user to read, rather than this feature also deciding what counts as "bad enough to flag," which risks conflicting with B3's already-established allergen-conflict-blocking UI pattern if done hastily. Both are reasonable, scoped follow-ups rather than gaps in this item itself.

**Verification**: 27 new unit tests (18 for `dri_service.py` -- BMR hand-calculations, every missing-field/fallback branch, fiber age/sex banding, the DB-backed latest-weight lookup; 9 for `compute_nutrition_summary` -- unscaled-by-servings behavior, same-day summing, week summing, skip/no-recipe exclusion, the entry-count-vs-contributing-count honesty check, sort order, null-value handling; 120 total in the repo, all passing). Live end-to-end pass against a freshly migrated+seeded database and a real local uvicorn instance: two household members (one with full body data, one missing weight+height), two recipes (one with nutrition data, one without), a 3-entry meal plan spanning two days -- confirmed day totals, week totals, the 2-entries-but-1-contributing case rendering both counts honestly, Jason's full DRI target computing correctly, and the second member's response correctly reporting `daily_targets: null` with `missing_fields: ["weight", "height"]` instead of being silently omitted. Frontend `npm run build` succeeds cleanly (53 modules, built from a `/tmp` scratch copy per the standing FUSE-mount note). **Not independently verified**: actual on-screen appearance/layout of the new table (no browser available, same standing limitation as every other UI-only change this project).

## B10.5 notes: Imperial/Metric/Weight unit toggle, density-sourcing (2026-08-01)

Picked as the next backlog item after B1.4, since its stated blocker (B1.1's food-database resolution layer, for the weight-mode density case) was already satisfied and it's within the higher-priority B10 (author-requested) group -- the same "pick the lowest-effort item with no remaining blocker" logic used to pick B10.6 over B10.5 itself a few sessions ago, now inverted now that the blocker is gone.

**`unit_conversion_service.py` gained `convert_for_display()`**, the shared per-view rendering layer both B5.3 and B10.5 were always meant to share (per the backlog's own cross-reference note). Given a quantity/unit and a target system ("metric" | "imperial" | "weight"), it picks the "nicest" unit via a simple magnitude heuristic -- the largest unit in that system's own ladder that keeps the rendered quantity >= 1 (e.g. 4 cups under the imperial ladder renders as "2 pt", not "0.03 gal") -- NOT full culinary fraction-rounding (no snapping to 1/4 cup), a documented, deliberate scope cut. "Weight" mode always targets grams/kg regardless of the Imperial/Metric choice, matching how a kitchen scale is actually used in GF baking (the entire point of the mode, per the original backlog text). Count-based units (`"2 cloves"`, `"1 can"`) always pass through unchanged -- a legitimate state, never treated as a failure.

**Density-sourcing, the piece B5.3 explicitly deferred**: `food_data_service._parse_usda_density()` scans a resolved food's USDA `foodPortions` list (fetched via the same `get_usda_food` detail call already made for nutrients) for the first portion reporting a recognized volume unit (cup, tbsp, etc.) and derives an implied density (g/mL) from its `gramWeight`. Verified USDA's actual `foodPortions` JSON shape live (searched rather than assumed, to avoid silently building a parser against a guessed schema) -- `amount`/`gramWeight`/`measureUnit.name`/`modifier` fields, as documented. Open Food Facts does NOT get a density in this pass (no consistently structured volume-portion data to parse there) -- a stated limitation, not an oversight. ## B10.2 notes: lightweight auth gate + in-app expiration digest (2026-08-01)

Picked as the next item after B10.3, leaving B10.1 (dining-out finder) as the only remaining B10 item -- it needs real design work (a new MealPlanEntry type, a location/radius UI) and depends on external network services (OSM Overpass, Tavily) this sandbox can't reach live, unlike B10.2's two pieces, both of which were fully buildable and testable here.

**Read Fiduciary's actual `auth.py`/`notifications.py` first, per the backlog's own instruction, rather than assuming their shape.** Both are substantial: `auth.py` is argon2 password hashing, TOTP MFA with single-use backup codes, a recovery-key flow, admin/viewer roles, rate limiting, and a host-CLI recovery/wipe tool -- built to protect real brokerage credentials. `notifications.py` is a full VAPID Web Push + generic-SMTP dispatch system keyed off an audit-log event stream. Both solve real problems for a financial app with actual attack surface and a compliance driver behind it.

**Checked scope with the author directly before building anything (via AskUserQuestion), rather than silently deciding to descope a security feature.** Chef's own backlog text for the absorbed items (B9.4: "ideally add optional single-password gating"; B4.4: "in-app banner at minimum; optional email/webhook") already describes something much lighter than literal Fiduciary parity, and Chef has no financial data behind it at all -- but "mirror Fiduciary" (B10.2's own phrasing) could reasonably be read the other way, so this wasn't a call to make unilaterally. The author confirmed: lightweight single-password gate, not full multi-user/MFA parity.

**Auth, built new for Chef's simpler model** (`auth_service.py`, `routers/auth.py`): one shared password (argon2-hashed, `argon2-cffi` new dependency), no per-user accounts, no MFA, no recovery keys, no host-CLI tooling. Defaults OFF (`is_enabled()` false until a password is explicitly set) so every existing install keeps working unchanged. The login rate limiter (`rate_limited`/`record_attempt`, an in-process sliding window) IS ported near-verbatim from Fiduciary's own `auth.py` -- genuinely domain-neutral, cheap insurance regardless of scope. Session state is a signed cookie via Starlette's `SessionMiddleware` (ships with FastAPI already, no new dependency beyond its own `itsdangerous` requirement) rather than re-deriving Fiduciary's own `request.session` usage from scratch. A single centralized `auth_gate` ASGI middleware in `main.py` enforces the session on every `/api/*` route except `/api/auth/status` and `/api/auth/login` -- deliberately NOT a per-router dependency sprinkled onto individual endpoints, which is the exact mistake Fiduciary's own `auth.py` docstring says its predecessor made (a token checked on only 23 of 127 endpoints). The password hash and enabled flag live in the existing `AppSetting` table under key names deliberately kept OUT of `settings_service.SETTING_SPECS` -- otherwise the generic `PATCH /api/system/settings/{key}` endpoint could overwrite the hash or silently flip auth on/off outside the dedicated, current-password-checked endpoints in `routers/auth.py`; a unit test asserts `is_known_key()` refuses both keys directly, not just via a router-level check.

**A real, independent CORS bug found and fixed while wiring this in**: `main.py`'s CORS config was `allow_origins=["*"]` with `allow_credentials=True`. Verified live via curl (with an `Origin` header) that Starlette's `CORSMiddleware` echoes back the literal string `"*"` for ordinary (non-preflight) responses in that configuration even with credentials on -- an invalid combination browsers refuse to honor for any credentialed request (a response can't say "any origin" AND "trust my cookies" at once). This would have silently broken session cookies in Chef's actual production topology (frontend and backend on different ports, no reverse proxy yet) the moment auth was ever turned on, with no equivalent problem visible in `curl` testing alone (browsers enforce this; curl doesn't) -- exactly the kind of bug that's easy to ship undetected without a browser to check against. Fixed by switching to `allow_origin_regex=".*"`, which always echoes the SPECIFIC request Origin instead of a literal wildcard; re-verified live that the fix produces a correct, specific `Access-Control-Allow-Origin` header. `frontend/src/api.js`'s fetch wrapper also gained `credentials: "include"`, without which the browser would never send/receive the cookie at all regardless of the CORS fix.

**A real middleware-ordering bug found and fixed the same way**: the first `auth_gate` implementation raised `AssertionError: SessionMiddleware must be installed` on every gated request once auth was enabled -- caught immediately by the live curl pass, not left for a browser to discover later. Root cause: Starlette's middleware stack makes the LAST-`add_middleware`-call the OUTERMOST layer (its request-phase code runs FIRST), the opposite of what a naive top-to-bottom reading of the file suggests. Fixed by registering the `auth_gate` dispatch function's `@app.middleware("http")` decorator BEFORE calling `add_middleware(SessionMiddleware, ...)`, so `SessionMiddleware` becomes outermost and populates `request.session` before `auth_gate` ever reads it -- documented directly in `auth_gate`'s own docstring so a future edit doesn't reverse it back.

**Notifications, scoped to the required minimum**: `inventory_service.get_expiring_digest()` reuses `compute_urgency()`'s existing expiration-day buckets (already built for `/priority-suggestions`) but filters to ONLY the expiration-driven reasons, split into `expired`/`expiring_soon`. New `GET /api/inventory/expiring-digest` endpoint; new `ExpiringDigestBanner.jsx` mounted in `App.jsx` outside `<Routes>` (same "stays alive across navigation" placement as `ChatWidget`) so it's visible from every page -- the actual gap the backlog named ("only surfaces passively when the user opens the Inventory page"). Web Push (VAPID) and SMTP email -- Fiduciary's own delivery channels -- are deliberately NOT built: the backlog's own text calls both "optional" and the in-app banner "at minimum," and Fiduciary's notification stack solves a materially different problem (fan-out for discrete security events via an audit-log hook) than "periodically check inventory for what's expiring," so porting it wholesale wasn't a good architectural fit even setting aside the added dependency (`pywebpush`/`py-vapid`) and complexity cost. Worth a follow-up if real usage shows the in-app banner alone isn't enough.

**Frontend**: `SettingsPage.jsx` gained a "Security" card (enable/change/disable, each requiring the current password where one already exists, mirroring the backend's own confirm-before-change discipline); `App.jsx` checks `/api/auth/status` on mount and renders `LoginGate.jsx` in place of the whole app when enabled-but-not-authenticated, re-checking status on a successful login rather than managing any client-side token (the httponly cookie is the entire mechanism).

**Deliberately not done**: TOTP/MFA, backup codes, recovery keys, multi-user accounts/roles, host-CLI recovery tooling (all confirmed out of scope with the author directly); Web Push and SMTP email notifications (documented above); tightening CORS to a concrete origin list instead of a regex (blocked on the still-open "no reverse proxy yet" simplification -- tightening now would mean hardcoding a port that changes per deployment).

**Verification**: 23 new unit tests (188 total in the repo, all passing) covering every `auth_service.py` branch (default-disabled, set/verify/change/disable password, the settings-registry-exclusion guard, rate-limiting with independent per-IP buckets) and every `get_expiring_digest` branch (expired-vs-expiring-soon split, "expires today" counting as expired not soon, sort order, configurable window, empty inventory). ## B11.1 notes: shared background job queue, everything unified (2026-08-01)

Ported the *architecture* (in-memory serial job registry, poll-based status endpoint, header badge) from the Fiduciary project's `portfolio-api/app.py`, adapted to Chef's stack: `backend/app/services/job_queue.py` is a new module, not a line-for-line port, since Chef's queue needed to be domain-generic across six unrelated endpoint kinds rather than Fiduciary's narrower use case. Deliberately **serial, not parallel**: the author's hardware (one local Ollama instance shared by both features) doesn't meaningfully parallelize two concurrent generations -- they'd split one GPU/VRAM budget, risking OOM and slowing both down -- so a single daemon worker thread pulls one `(job_id, fn)` at a time off a `queue.Queue`. Deliberately **in-memory, not a DB table**: job status is transient operational state, not durable business data; a job's actual result (an inventory row, a recipe, a chat message) is written through the exact same commit path every other write in the app already uses, and a job lost to a container restart has to be resubmitted regardless of what persistence strategy was chosen, since there's no realistic way to checkpoint "a receipt photo was 60% analyzed."

**Every AI-consuming endpoint now enqueues instead of blocking**, returning `202 {job_id, status, created}` immediately: `inventory.vision_intake`/`import_inventory`, `recipes.import_recipe`/`chat_about_recipe`, `chat.send_message`, `meal_plan.generate_meal_plan`. `knowledge.upload_knowledge_file` is the one exception to the "returns a job_id" pattern -- it keeps its original `KnowledgeFileRead`/201 response contract (the file row itself isn't gated on indexing) and just moves the reindex call into a fire-and-forget job, since the frontend already showed an "indexing..." tag driven by `chunk_count == 0` with no prior polling mechanism to disturb. The conversion pattern, applied consistently: fast synchronous pre-flight validation (input presence, 404 checks) stays on the request thread; everything else moves into a `_run()` closure that opens its own `SessionLocal()` rather than reusing the request-scoped `db` dependency, since a SQLAlchemy ORM object is bound to the session that loaded it and isn't safe to hand across threads -- anything the closure needs from the request's own session is snapshotted to a plain dict/Pydantic model before the closure is defined, never passed as a live ORM object. Errors that used to get distinct HTTP status codes now surface uniformly as job `status="error"` with a message, since that distinction only mattered for synchronous HTTP semantics these endpoints no longer have. Found and fixed a real, unrelated bug while doing this: `chat_about_recipe` had picked up a duplicate stacked `@router.post` decorator during the conversion (an editing slip, not a design choice) that would have registered the same route twice with two different response models -- caught by rereading the file before calling it done, not by a test.

**Dedup via `dedup_key`**: `enqueue()` coalesces a new submission into an existing queued/running job of the same key rather than starting a race -- used for chat (`dedup_key=f"chat:{session_id}"`) so two sends against the same growing session history can't run concurrently and interleave incorrectly. Live-verified: firing two chat sends back-to-back for the same session returns the identical `job_id` with `created: false` on the second.

**Frontend**: `useBackgroundJob(storageKey)` (new hook) persists an in-flight job's id to `localStorage`, polls `GET /api/jobs/{id}` every 1.5s, and -- the actual fix for the reported "page goes blank after tab-switching away and back" bug -- resumes polling automatically on mount if it finds a leftover job id, since the job keeps running server-side regardless of whether any page is watching it. Wired into every converted endpoint's corresponding UI: `InventoryPage.jsx` (vision intake + receipt/list import), `RecipesPage.jsx` (import) and `RecipeChat.jsx` (recipe-scoped chat, storageKey scoped per recipe id), `ChatWidget.jsx` (persistent chat, storageKey scoped per session id -- notable because this widget is mounted once at the `App.jsx` shell level and never unmounts on route changes, so it now survives both navigation AND a full page reload), and `MealPlanPage.jsx` (generation). A new `JobsBadge.jsx`, mounted the same "outside `<Routes>`" way as `ChatWidget`/`ExpiringDigestBanner`, polls `GET /api/jobs` every 2s and shows the running job's label plus an ETA derived from `_typical_seconds()` (the median duration of the last 5 completed jobs of the same kind, or an honest "no history yet" until one exists) -- this is the app-wide "something is happening" indicator the author's bug report asked for, visible from any page regardless of which page enqueued the work. New `@keyframes chef-spin`-backed `.busy-spinner`/`.jobs-badge-spinner` CSS classes in `theme.css`, using `color-mix`/`currentColor` so they render correctly across all ~12 shipped themes without per-theme overrides.

**Verification**: 9 new backend unit tests (`test_job_queue.py`, 223 total, all passing) exercising the queue directly against its real background thread with real `time.sleep()` synchronization rather than mocks, since real concurrency behavior was the point -- covering success, exception-capture, worker-survives-a-failed-job, strict serial (not concurrent) execution, both dedup branches, unknown-job 404 shape, and the progress/ETA computation. A live end-to-end pass against a freshly migrated database and a real local uvicorn instance (after discovering and fixing three more `/app`-hardcoded default paths that don't exist in this sandbox -- `DATABASE_URL`, `SECRETS_KEY_FILE`/`SECRETS_KEYRING_FILE`, `SESSION_SECRET_FILE`, all already env-overridable, just not previously exercised from a non-Docker environment) confirmed: a recipe import, a chat send, and a meal-plan generation submitted back-to-back all enqueue into the SAME shared queue and are visibly, correctly processed one at a time (`GET /api/jobs` mid-run showed one `running` + one `queued` + one already `error`-terminal, in FIFO order across three completely different endpoint kinds) -- this is the literal scenario from the author's bug report ("upload a receipt, then ask Chef chat a question, then go mess with recipes") and it now queues cleanly rather than any earlier request dying; the queue drained back to idle afterward with no stuck jobs. Every enqueued job in this sandbox terminates in `status: "error"` (`[Errno -3] Temporary failure in name resolution`) since no live Ollama reaches this sandbox -- sufficient to prove the plumbing (enqueue -> worker pickup -> error capture -> visibility) but not model output quality, an honestly-stated limitation shared with every other AI-endpoint verification in this project. Frontend `npm run build` clean across all six touched/new files. **Not verified**: on-screen appearance of the spinner/badge/resume-on-navigation behavior in an actual browser (no browser available, the standing limitation on every UI change in this project) and real Ollama generation quality through the new queue.
