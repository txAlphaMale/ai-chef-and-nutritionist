## What this is

A locally hosted, AI-driven, web-connected meal planning, food inventory, and recipe management app for a household (default 2 people). Runs via Docker Compose. Ships on GitHub so others can pull it down and self-host. Uses Ollama for local LLM inference and Tavily for web search grounding.

That prototype is not part of this repo. Some of its design patterns (interactive tool surface, autonomous weekly meal-plan job, avoiding spreadsheet-as-database) were salvaged and are reflected in the decisions below.

## Architecture decisions (confirmed 2026-07-30)

## Phase 3 notes: inventory

Backend (`backend/app/routers/inventory.py`, `app/services/inventory_service.py`, `app/schemas/inventory.py`):

- Full CRUD: `GET/POST /api/inventory`, `GET/PATCH/DELETE /api/inventory/{id}`, with `category`/`is_priority`/`search` filters on the list endpoint.
- **Urgency scoring** (`compute_urgency`): points for expired (100) / expiring ≤3d (80) / ≤7d (50) / ≤14d (20) days, staleness (unused >60d: 30, >30d: 15), and the `is_priority` flag (25) — plus human-readable reasons. `GET /api/inventory/priority-suggestions` returns items ranked by this score; the meal-planning engine (Phase 5) is meant to consume the same function directly, not just the endpoint.
- **Vision photo intake**: `POST /api/inventory/vision-intake` sends the uploaded image + a JSON-array-only prompt to the configured Ollama vision model and returns a *preview* (nothing written to inventory yet). `POST /api/inventory/vision-intake/confirm` bulk-creates from a (user-reviewed/edited) item list. Response parsing (`parse_vision_response`) is defensive — tries strict JSON, falls back to extracting the first `[...]` block — because real vision-model output often wraps JSON in prose/markdown fences; unit-tested against both cases plus garbage input and an invalid category value.
- **Deduction primitive** (`deduct_by_name`): case-insensitive exact-then-substring match against inventory by name, decrements quantity floored at 0, stamps `last_used_date`. This is what Phase 5 (confirming a meal-plan entry) and Phase 7 (chat: "we made X" / "we're out of Y") will call — matching recipe ingredient names to inventory names is inherently fuzzy; a smarter matcher (aliases, unit conversion) is a documented future improvement, not attempted here.

Frontend (`frontend/src/pages/InventoryPage.jsx`, `components/InventoryItemForm.jsx`): category filter, add/edit form (shared component), delete, and a photo-upload flow that shows the detected-items preview before anything is committed. Rows are color-coded by urgency score using the same reasons the backend computed. Switched to `HashRouter` (was a single static page) with a nav bar for Home/Inventory.

**Known simplification: frontend/backend origins.** Docker Compose runs `frontend` (5173) and `backend` (8095) as separate containers with no reverse proxy between them. In dev (`npm run dev`), the vite proxy in `vite.config.js` makes `/api/*` and `/health` same-origin. In the production Docker build, `frontend/src/api.js` falls back to hitting the backend directly at `${hostname}:8095` (hardcoded port, matching `.env`'s `BACKEND_PORT` default) using the backend's wide-open CORS. This works for the common single-host case but is fragile if `BACKEND_PORT` is changed without updating `api.js` too, and doesn't support serving over HTTPS/a real domain cleanly. A shared reverse proxy (nginx/Caddy sidecar, single external port) is a reasonable Phase 9 packaging improvement.

**Verification:** unit tests for `parse_vision_response` (4 cases) and `deduct_by_name` (exact match, fuzzy match, no match, floor-at-zero) run directly against the service module; full CRUD + priority-suggestions + bulk vision-confirm exercised via curl against a live local uvicorn instance; `vision-intake` itself confirmed to fail cleanly with a 502 (no live Ollama in the sandbox) rather than crashing. Frontend: `npm run build` succeeds; ran the real Vite dev server against the real backend together and hit `/health` and `/api/inventory` (including a POST) through the actual proxy path the browser will use, not just each side in isolation.

## Operational note: bash sandbox / native file coherence

Claude's bash sandbox sees this folder through a FUSE mount that can cache stale file sizes -- if Claude edits a file with the Read/Write/Edit tools and then reads/git-adds/executes it via bash in the same session, the bash side can occasionally get truncated/stale content instead of the true file (documented and verified in the sibling Fiduciary project, `docs/COWORK-FUSE-COHERENCE.md`). Checked on 2026-07-30: every file that had been through this mixed edit pattern so far (`config.py`, `main.py`, `.gitignore`, `README.md`, `.env.example`, `seed.py`, this file) was verified intact -- Read tool content matched `git show HEAD:<path>` exactly, no corruption found. Going forward, prefer a single writer surface (bash heredoc/sed, or the Edit/Write tool) per file for its whole edit-test-commit cycle, and spot-check with the Read tool before trusting a bash-side commit of a file that was just edited natively.

## Phase 1 schema notes

15 tables, defined under `backend/app/models/` (one file per domain area) and imported through `app/models/__init__.py` so Alembic autogenerate and relationship string-lookups both see the full set:

- **inventory.py** — `InventoryItem` (category, quantity/unit, location, purchased/expiration/last-used dates, `is_priority` flag + note for "use this up" boosting, source of entry: manual/vision/chat).
- **kitchen.py** — `KitchenProfile` (name, JSON equipment list, `is_active`) for home vs. camping/RV/rental setups.
- **recipe.py** — `Recipe` (default_servings for scaling, JSON instructions list, JSON nutrition dict, rating, `is_staple`, source), `RecipeIngredient`, `MealTag` + `recipe_tag_links` join table (seeded tags: quick, portable, non_refrigerated, dutch_oven_only, backpacking, one_pot, make_ahead, freezer_friendly, kid_friendly, gluten_free).
- **meal_plan.py** — `MealPlan`, `MealPlanEntry` (day/meal_type/recipe/servings, `is_confirmed` is the hook that should trigger inventory deduction in Phase 3, `is_skipped` for chat-driven skip handling), `GroceryListItem`.
- **household.py** — `HouseholdPreferences` (singleton row, household_size default 2, dietary_restrictions JSON, goals, indulgence_frequency), `HouseholdMember` (age/height/sex/activity_level for BMI-aware planning in Phase 6).
- **health.py** — `HealthMetricEntry` (weight, BMI, LDL/HDL/total cholesterol, triglycerides, blood pressure, glucose) tied to a household member, for Phase 6 trend charts.
- **chat.py** — `ChatMessage` (session_id, role, content, timestamp) backing the persistent/background chat in Phase 7.
- **settings.py** — `AppSetting` (key/value/is_secret, for the Settings GUI in Phase 8), `SystemPrompt` (prompt_key: `main_chef` / `dietary_onboarding`, editable content — Phase 2 wires these into the Ollama client), `KnowledgeFile` (imported nutritionist grounding docs, Phase 6).

**Seed data is deliberately generic**, not the author's personal profile — `HouseholdPreferences` seeds with household_size=2 and no dietary restrictions pre-filled, since this repo is meant for other households to pull down and configure for themselves via onboarding/Settings. The `main_chef` and `dietary_onboarding` system prompts are seeded with real content per the project brief (nutritionist-chef persona, confirm-before-write, expiring/priority-ingredient bias, occasional indulgence).

`backend/docker-entrypoint.sh` runs `alembic upgrade head` then `python -m app.seed` (both idempotent) before starting uvicorn, so the DB bootstraps itself on first `docker compose up` and stays current on every restart without manual steps.

## Settings & secrets storage

Ported from `Fiduciary/portfolio-api/secrets_crypto.py` (a validated, tested module in the author's sibling project, read directly on 2026-07-30 — not reinvented from scratch) into `backend/app/services/secrets_crypto.py`:

- Fernet (AES-128-CBC + HMAC, via the `cryptography` package) symmetric encryption for any `AppSetting` row where `is_secret=True` (currently just `tavily_api_key`).
- Key file at `/app/data/secrets.key` (same Docker volume as the SQLite DB), generated on first run, written atomically with 0600 permissions. **Losing this file makes every encrypted value permanently unrecoverable** — back it up alongside `./data`.
- Versioned envelope encryption from day one so key rotation is possible later without a bulk re-encrypt: unrotated deployments produce unprefixed ciphertext (the common case); `rotate_key()` adds a new key version to `/app/data/secrets_keyring.json`, all new encrypts use it, old ciphertext keeps decrypting under its original key forever.
- `decrypt_or_legacy()` never raises — falls back to returning the raw value if it isn't a valid token, for defensive handling of pre-encryption data.

`backend/app/services/settings_service.py` wraps this with a `SETTING_SPECS` registry (key, label, `is_secret`, default, description, optional `.env` fallback name) and `get_setting()`/`set_setting()`/`list_settings_for_display()` (secrets masked as `********` for API responses). `app/seed.py` uses this to seed each setting once — from an optional `.env` value if present, otherwise the spec default — and never overwrites a value that already exists, whether set via `.env` or later via the Settings UI (Phase 8).

`app/config.py` (pydantic `Settings`) now holds ONLY true infra bootstrap values (`database_url`, `backend_port`) that must exist before the DB is reachable. Everything else moved out of it: Ollama base URL/models and the Tavily key are DB-backed via `settings_service`; household size lives in `HouseholdPreferences` (already the case since Phase 1).

`app/services/ollama_client.py` and `app/services/tavily_client.py` are thin wrappers that pull their config from `settings_service` per-call (not cached at import time), so a Settings UI edit takes effect on the next request without a restart.

**Known sandbox-only quirk (not a bug):** importing the `ollama` package fails inside Claude's sandbox because ambient `ALL_PROXY=socks5h://...` env vars (from the sandbox's own network setup) break `ollama`'s eager default-client construction at import time. Confirmed this doesn't happen with those proxy vars unset, and the real Docker deployment won't have them set. Local verification of `ollama_client.py`/`tavily_client.py` therefore ran with `env -u ALL_PROXY -u ...`; no code changes were needed to work around it.

## Phase 4 notes: recipes

Backend (`backend/app/routers/recipes.py`, `app/services/recipe_service.py`, `app/schemas/recipe.py`):

- Full CRUD: `GET/POST /api/recipes`, `GET/PATCH/DELETE /api/recipes/{id}`, with `is_staple`/`tag`/`search` filters. `POST /{id}/rating` validates 1–5 (422 outside that range).
- **Servings scaling**: `GET /api/recipes/{id}?servings=N` returns ingredient quantities scaled by `N / default_servings` (`scale_ingredients`) — nutrition is stored per-serving already (see Phase 1 schema notes) so it's returned as-is, not multiplied. `None`-quantity ingredients (e.g. "salt to taste") pass through unscaled rather than erroring.
- **Tags**: get-or-create by name (`resolve_tags`) — reusing an existing tag name (e.g. one of the 10 seeded in Phase 1) does not create a duplicate `MealTag` row, verified directly against the DB.
- **AI-assisted import** (`POST /api/recipes/import`, multipart): accepts a `text` form field OR an uploaded file, dispatching by content type — images go to the Ollama vision model, PDFs are text-extracted via `pypdf` then sent to the chat model, plain text files are decoded and sent to the chat model. Returns a *preview* (`RecipeImportResponse`), nothing is saved until the user reviews/edits and the frontend POSTs to the normal create endpoint — same preview-then-confirm pattern as Phase 3's vision intake. `parse_recipe_response` defensively extracts a JSON object from real-world model output (prose/markdown-wrapped or strict), returning `None` (→ 422) only if no usable title is found.
- **Bug caught and fixed during testing**: the `/import` endpoint mixes an `UploadFile` with a plain `text` parameter, which requires `text: str | None = Form(None)` — without explicit `Form()`, FastAPI silently treats `text` as a query parameter and never reads it from multipart form data. Caught by an actual failing curl test (400 "provide text or file" despite sending text), not by inspection.

Frontend (`frontend/src/pages/RecipesPage.jsx`, `RecipeDetailPage.jsx`, `components/RecipeForm.jsx`): list with search/staple filters, a shared add/edit form (dynamic ingredient and instruction rows, comma-separated tags, optional per-serving nutrition), an import panel (paste text or upload photo/PDF, review the parsed preview before saving), and a detail page with a live servings input that re-fetches scaled quantities, a rating dropdown, and a staple toggle. Routing extended with `/recipes` and `/recipes/:id`.

**Verification:** unit tests for `parse_recipe_response` (strict JSON, markdown-wrapped, garbage, missing-title) and `scale_ingredients` (up-scale, down-scale, no-op, `None` quantity untouched) run directly; full CRUD, rating validation, staple/tag filters, and tag deduplication exercised via curl against a live backend; the `Form()` bug found and fixed via a live request, then re-verified; frontend build succeeds; ran the real Vite dev server against the real backend and created/scaled a recipe through the actual proxy path.

## Phase 4.1 notes: recipe chat, citations, URL import, tips

Added after Phase 4 shipped, in response to a specific follow-up request: an ephemeral chat for substitution questions while cooking, source citation capture for copyright respect, URL import, and a way to retain genuinely useful asides (substitutions/variations) from imported sources while discarding ads/stories/boilerplate.

**Schema** (migration `957de2f3c51d`): `Recipe` gained `source_url` (String 1000, nullable), `source_name` (String 200, nullable), `source_author` (String 200, nullable), and `tips` (JSON list, default empty). `RecipeBase`/`RecipeUpdate` schemas extended to match; `RecipeIngredientRead.id` changed to `int | None` since scaled (non-persisted) ingredient views don't have a real row id.

**URL import**: `recipe_service.extract_url_content(url)` splits into `fetch_html()` (network call via `trafilatura.fetch_url`) and `extract_content_from_html()` (pure function over HTML using `trafilatura.bare_extraction`, `favor_recall=True`) so the extraction logic is unit-testable without a live network call. `trafilatura` does the mechanical boilerplate removal (ads/nav) and captures byline/sitename metadata in the same pass — that metadata becomes the citation (`source_url`/`source_name`/`source_author`) rather than being discarded. `POST /api/recipes/import` now accepts `text`, `file`, or `url` (exactly one; `url` is checked first) as multipart form fields.

**Copyright-respecting parsing**: `RECIPE_IMPORT_PROMPT` explicitly instructs the model to extract only factual/functional recipe data (what to buy, what to do, timing) and NOT reproduce narrative prose, personal stories, ads, or other copyrightable writing — summarizing functionally instead of quoting at length. A new `tips` array in the prompt output captures genuinely useful asides (substitutions, optional variations, storage/make-ahead notes, equipment alternatives) as short paraphrases, omitted entirely if the source has nothing like that. Verified with a synthetic HTML fixture containing a fake ad, nav, personal story, and an embedded substitution tip: ad/nav were stripped by trafilatura, the substitution text survived into extracted text, and title/author/sitename metadata were captured correctly.

**Bug fixed**: `parse_recipe_response` previously hardcoded `"source": "import_text"` in its return dict regardless of the actual import method, mislabeling image/PDF/URL imports. Fixed by removing that key from the service function entirely; the router now sets `parsed["source"]` based on which import branch actually ran (`import_text` / `import_file` / `import_image` / `import_url`).

**Ephemeral recipe-scoped chat** (`POST /api/recipes/{id}/chat`): for in-the-moment questions like "I'm out of buttermilk, what can I use?" while cooking. Deliberately NOT persisted to the `chat_messages` table — that's reserved for the Phase 7 persistent/background chat system, a separate concern. The client (`RecipeChat.jsx`) holds conversation history only in React state and resends it each turn to this stateless endpoint. `recipe_service.build_recipe_chat_context()` builds a context block (title, ingredients at the currently-viewed serving size, numbered instructions, known tips) that's appended to the active `main_chef` system prompt, so suggestions are grounded in the actual recipe rather than generic. Widget is collapsed by default on the recipe detail page, Enter-to-send (Shift+Enter for newline).

**Frontend**: `RecipeForm.jsx` gained editable tips list and source fields (auto-filled on import, editable manually); `RecipesPage.jsx` gained a URL input alongside the existing text/photo/PDF import controls, with a hint explaining the ad/story filtering behavior; `RecipeDetailPage.jsx` displays tips and a source citation (linked if a URL is present) below the nutrition block, and mounts `RecipeChat` at the bottom of the page; `theme.css` gained matching styles for the chat widget and citation text.

**Verification**: backend — unit tests for `extract_content_from_html` against the synthetic HTML fixture described above, `build_recipe_chat_context` against a mocked recipe (asserts title/ingredient text present in the built context), and the full import/chat flow via curl against a live local uvicorn instance (mocked `ollama_client.chat`/`describe_image` since no live Ollama reaches the sandbox) covering url/text/file import dispatch and the new `source`/citation labeling; a nested-f-string Python 3.10 SyntaxError in `build_recipe_chat_context` was caught by `py_compile` before runtime testing and fixed by extracting a plain-concatenation helper (`_format_ingredient_line`). Frontend — `npm run build` succeeds cleanly; ran the real Vite dev server against a real backend (fresh SQLite DB, real Alembic migration + seed, mocked Ollama chat response) together and exercised `/health`, recipe create, servings-scaled GET (confirmed tips/citation fields and scaled quantities round-trip correctly), and `POST /{id}/chat` all through the actual browser-facing Vite proxy path — not just each side tested in isolation.

## Phase 5 notes: meal planning engine

Backend (`backend/app/routers/meal_plan.py`, `app/routers/kitchen.py`, `app/services/meal_plan_service.py`, `app/schemas/meal_plan.py`, `app/schemas/kitchen.py`):

**Schema** (migration `67a6d7e5b6e5`): `MealPlanEntry` gained `requested_tags` (JSON list -- the guiding tags a slot was planned against, e.g. `["portable", "non_refrigerated"]` for a picnic) and `is_indulgence` (marks the week's occasional treat meal, separate from `HouseholdPreferences.indulgence_frequency` which just sets the target cadence). `GroceryListItem` gained `category` (nullable, mirrors `InventoryItem` categories, for a future group-by-aisle view). `MealPlan`/`MealPlanEntry`/`GroceryListItem` tables themselves already existed from the Phase 1 schema but had never been wired to an API until now.

**Kitchen profiles** (`routers/kitchen.py`, new): simple CRUD the project brief calls for but no earlier phase built -- `GET/POST /api/kitchen-profiles`, `PATCH/DELETE /api/kitchen-profiles/{id}`. Only one profile is active at a time; setting one active clears the flag on the others (same singleton-ish pattern as `HouseholdPreferences`). This is what lets the meal planner adapt to a home kitchen vs. camping/RV/rental with limited equipment.

**Generation** (`POST /api/meal-plans/generate`): same preview-then-confirm pattern as recipe import -- returns a `MealPlanCreate`-shaped preview, nothing persisted until the user reviews/edits and `POST`s to `/api/meal-plans`. `meal_plan_service.gather_generation_context()` pulls together everything the model needs to ground a sensible plan: household size/dietary restrictions/goals/indulgence frequency, the active (or requested) kitchen profile's equipment list, `inventory_service.get_priority_suggestions()` (the same urgency-scoring function built in Phase 3, reused directly rather than reimplemented) for what to prioritize using up, and a compact recipe catalog (staples and highly-rated first) so the model can reuse an existing recipe instead of inventing one for every slot. The prompt instructs the model to strongly prefer an existing catalog `recipe_id` and only propose a `new_recipe` (same shape as recipe import, via the now-shared `recipe_service.coerce_recipe_fields()`) when nothing fits. Per-slot guidance (e.g. "Saturday lunch needs to be portable for a picnic") and free-text notes (e.g. "going camping this weekend") can steer generation.

**Defensive parsing carries a validation step recipe import didn't need**: `parse_meal_plan_response()` coerces fields the same defensive way as recipe import (strict JSON first, then extract the first `{...}` block), but a meal plan additionally references *existing* recipe ids the model was shown -- and models sometimes hallucinate one that wasn't in the catalog. `validate_entries_against_catalog()` nulls out any `recipe_id` not actually present in the catalog that was sent, rather than trusting it; the slot is then left recipe-less for the user to fix in the review step, same as any other AI-preview-then-confirm flow here. Verified with a live curl test using a mocked Ollama response that deliberately includes a fabricated id (999) alongside two valid slots (one reusing a catalog recipe, one proposing a `new_recipe`) -- confirmed the hallucinated id came back `null` while the other two passed through correctly.

**Grocery list derivation**: split the same way as recipe import's URL extraction -- a pure aggregation/subtraction pair (`aggregate_ingredients`, `subtract_inventory`) that's unit-testable without a DB, plus a thin `compute_grocery_list()` wrapper that loads a persisted plan's entries/inventory. Ingredients are scaled to each entry's servings (reusing `recipe_service.scale_ingredients`), summed across all non-skipped entries keyed by `(name, unit)`, then matched against current inventory the same case-insensitive exact-then-substring way as `inventory_service.deduct_by_name` and subtracted; only the remaining (still-needed) quantity is listed. An ingredient with no stated quantity (e.g. "salt to taste") is only listed if nothing matching exists in inventory at all, rather than always appearing. Recomputation happens automatically on plan creation, on any entry edit/skip (`_persist_grocery_list()` replaces `source="auto"` rows only, leaving manually-added items alone), and on-demand via `POST /{plan_id}/grocery-list/regenerate` (e.g. after a shopping trip). Verified: confirming a meal deducts its scaled ingredients from inventory (reusing `inventory_service.deduct_by_name` once per ingredient) and a subsequent grocery-list regeneration correctly reflects the now-lower on-hand quantity -- i.e. the grocery list always answers "what do I still need to buy for everything not yet skipped," not a frozen snapshot from generation time.

**New-recipe creation on confirm**: `recipe_service.create_recipe_from_parsed()` (new, shared) creates a `Recipe` + ingredients + tags from a `coerce_recipe_fields()`-shaped dict without duplicating `routers/recipes.py`'s creation wiring wholesale -- used when `POST /api/meal-plans` persists an entry whose slot had no catalog match, tagging the new recipe `source="ai_generated"`. Verified live: a generated plan's `new_recipe` entry actually appears in `GET /api/recipes` afterward with the correct source label and is immediately available for future weeks' catalogs.

**Confirm/skip**: `POST /{plan_id}/entries/{entry_id}/confirm` marks a meal as made and deducts its scaled ingredients from inventory (best-effort -- an ingredient with no inventory match is silently skipped rather than failing the whole confirmation); `/skip` marks it skipped with no deduction. Both are blocked once an entry is already confirmed (400), and skip is blocked on an already-confirmed entry, verified via live curl including the double-confirm 400 case. Deleting a plan cascades to its entries (existing `cascade="all, delete-orphan"` relationship from Phase 1), verified live.

Frontend (`frontend/src/pages/MealPlanPage.jsx`, `components/MealPlanEntryRow.jsx`, `components/GroceryListPanel.jsx`): a plan picker (dropdown over existing plans by week), a generate form (week start date, household size override, kitchen profile select, meal-type checkboxes, free-text notes, and a collapsible per-day tags/notes guidance section), an editable review step after generation (swap any slot between the AI's proposed new recipe and any catalog recipe, adjust servings/tags/indulgence flag, nothing saved until confirmed), a weekly grid for the persisted plan (recipe swap, servings, "we made this"/skip actions, linking through to the recipe detail page), and a self-contained grocery list panel (checkbox to mark purchased, manual add, delete, recompute-from-inventory). Nav/routing extended with `/meal-plan`. `theme.css` gained matching styles for the grid, preview rows, and grocery list, following the existing "single source of truth" CSS-variable convention.

**Verification**: unit tests for the pure functions (`parse_meal_plan_response` against strict/markdown-wrapped/garbage/invalid-day input, `validate_entries_against_catalog`, `aggregate_ingredients`, `subtract_inventory`, `build_generation_prompt`) run directly against the service module; a comprehensive live curl sequence against a fresh local backend (real Alembic migration + seed, mocked `ollama_client.chat` returning a canned plan with a catalog-reuse slot, a new-recipe slot, and a deliberately hallucinated recipe id) covering generation, plan creation (including new-recipe auto-creation), grocery-list aggregation/subtraction math (hand-verified the exact expected quantities at each step), confirm-triggered inventory deduction, skip, manual grocery items, regeneration, entry PATCH re-syncing the grocery list, 404s, and cascade delete; kitchen-profile CRUD and active-exclusivity verified live; frontend `npm run build` succeeds cleanly; a full live Vite-dev-server + real-backend pass exercised health, kitchen-profiles, recipe creation, plan generation, plan creation, grocery-list retrieval, and entry confirmation all through the actual browser-facing proxy path.

## Phase 6 notes: health & nutrition tracking

Backend (`backend/app/routers/household.py`, `app/routers/health.py`, `app/routers/knowledge.py`, `app/services/health_service.py`, `app/services/knowledge_service.py`, `app/schemas/household.py`, `app/schemas/health.py`, `app/schemas/knowledge.py`):

**Schema** (migration `a4a23dff4e5e`): `KnowledgeFile` gained `content` (Text, nullable -- extracted plain text, populated once at upload rather than re-parsed on every request) and `is_active` (Boolean, default true -- only active files ground generation). `HouseholdPreferences`, `HouseholdMember`, and `HealthMetricEntry` already existed from the Phase 1 schema but had no API until now.

**Household preferences & members** (`routers/household.py`, new): `GET/PATCH /api/household/preferences` for the singleton row (household size, dietary restrictions, goals, indulgence frequency), `GET/POST /api/household/members` + `PATCH/DELETE /api/household/members/{id}` for per-person profiles (age, height, sex, activity level) that both BMI calculation and meal-plan generation draw on.

**Health metrics & BMI** (`routers/health.py`, new): `GET/POST /api/health/metrics` (optionally filtered by member) and `PATCH/DELETE /api/health/metrics/{id}`. BMI is deliberately never accepted from the client -- `_compute_bmi_for_entry()` always computes it server-side from the submitted `weight_kg` and the associated member's `height_cm` (`health_service.compute_bmi`), so it can't drift out of sync if the member's height is corrected later, and is recomputed on any `PATCH` that changes `weight_kg` or `household_member_id`. Weight is stored canonically in kg (matches the existing model); the frontend (`HealthPage.jsx`) converts to/from pounds for display and entry, since a US household is the primary near-term user, without baking imperial units into the schema.

**Trend computation** (`GET /api/health/trends?household_member_id=`): `health_service.compute_metric_trend()` compares the most recent data point for a field against the oldest point still within a rolling window (default 90 days), falling back to the earliest point overall if none fall inside the window -- e.g. "down 3.5kg over the last 90 days" rather than a naive first-vs-last-ever comparison that could span years. Returns `null` for a field with fewer than 2 data points rather than a misleading zero-delta. Covers weight, BMI, LDL, HDL, and total cholesterol in one response.

**BMI/health-aware meal planning**: `health_service.build_health_context_summary()` builds a compact per-member line (e.g. "Jason: weight 94.5kg, BMI 29.2 (overweight), LDL 128.0 mg/dL ... weight down 3.5kg over the last 90 days") from the same trend function, and `meal_plan_service.gather_generation_context()` (Phase 5) now includes it as `health_summary`, injected into the generation prompt via a new section instructing the model to let it quietly bias toward lower-cholesterol, appropriately-portioned choices without mentioning the numbers directly to the user. This directly closes the loop the project brief asked for: body metrics actually steering plan generation, not just being logged and forgotten.

**Nutritionist knowledge files** (`routers/knowledge.py` + `services/knowledge_service.py`, new): `POST /api/knowledge-files` (multipart upload) stores the raw file on disk under a UUID-based name (`knowledge_service.save_file`, same atomic-write pattern as `secrets_crypto.py`'s key file, avoiding filename-collision/traversal issues from user-supplied names) and extracts plain text once at upload time (`knowledge_service.extract_text` -- reuses `recipe_service.extract_pdf_text` for PDFs rather than duplicating pypdf plumbing; `.txt`/`.md` decoded directly; anything else stored but left ungrounded, `has_content: false`, not an upload error). `GET /api/knowledge-files` never returns the full extracted text (`content_excerpt` is a 300-character preview only); `PATCH` toggles `is_active`/edits the description; `DELETE` removes both the DB row and the file from disk.

**Knowledge-file grounding**: `health_service.build_knowledge_context()` concatenates every *active* file's extracted text (truncated to a combined 3000-character budget via `_format_knowledge_excerpts`, each chunk labeled with its filename) and `gather_generation_context()` includes it as `knowledge_context`, injected into the generation prompt as reference material the model should follow where it doesn't conflict with stated dietary restrictions. **Documented simplification**: this is simple concatenation-with-truncation, not retrieval -- fine for a handful of short reference documents (a doctor's guidance sheet, a specific diet plan) but would need real chunking/embedding-based retrieval to scale to a large knowledge base. Noted here for a future pass rather than over-built now.

Frontend (`frontend/src/pages/HealthPage.jsx`, `components/TrendChart.jsx`, `components/KnowledgeFilesPanel.jsx`): household preferences editor, member add/remove list, a per-member metric-logging form (date, weight in lbs, LDL/HDL/total cholesterol, triglycerides, blood pressure, glucose) with a history table (delete per entry), two `TrendChart` sparkline-style panels (weight, LDL) built as plain inline SVG rather than adding a charting library dependency -- the app has stayed dependency-light through five phases and the data volumes here (a handful of log entries) don't warrant one; gracefully shows "not enough data yet" below 2 points instead of erroring. `KnowledgeFilesPanel` (upload/list/activate-toggle/delete) is self-contained like Phase 5's `GroceryListPanel`. Nav/routing extended with `/health`. `theme.css` gained matching styles for member rows, trend charts, and the knowledge file list.

**Verification**: unit tests for the pure functions (`compute_bmi`, `bmi_category`, `compute_metric_trend` against within-window/outside-window/fallback-to-earliest/insufficient-data cases, `format_member_health_line`, `_format_knowledge_excerpts` truncation) run directly against the service modules; a live curl sequence against a fresh local backend covering preferences update, member CRUD, metric logging with server-computed BMI verified against a hand-calculated expected value, the trends endpoint, knowledge-file upload/list/deactivate/delete (including confirming the file is actually removed from disk), and 404s; **directly verified the generation prompt itself contains the injected health and knowledge grounding text** (not just that the context dict was built) by calling `gather_generation_context` + `build_generation_prompt` against the live test DB and asserting the member's name/BMI/trend and the uploaded file's content appear in the resulting prompt string; frontend `npm run build` succeeds cleanly; a full live Vite-dev-server + real-backend pass exercised preferences, member creation, metric logging, and knowledge-file upload/list through the actual browser-facing proxy path. ## Phase 7 notes: persistent chat system

Backend (`backend/app/routers/chat.py`, `app/services/chat_service.py`, `app/schemas/chat.py`):

**Schema** (migration `5c07836d9339`): `ChatMessage` (already existed from the Phase 1 schema, unused until now) gained `actions` (JSON, nullable) -- structured action proposals attached to an assistant message, so history replay after a page reload can still show actionable cards, not just the reply text. Always null on user messages.

**Sessions are implicit, not a separate table**: a session is just a distinct `session_id` value already present in `chat_messages`. `GET /api/chat/sessions` derives a summary (message count, last-message time, a truncated preview) with a `GROUP BY`, ordered most-recent-first; `DELETE /api/chat/sessions/{id}` deletes all rows for that id. The frontend generates its own `session_id` (`crypto.randomUUID()`, persisted in `localStorage`) rather than calling a `POST /sessions` endpoint -- a session only "exists" server-side once its first message is sent.

**Context grounding**: `chat_service.build_chat_context()` pulls the currently-relevant meal plan (the `active`-status one if there is one, else the most recently created plan at all, so chat is still useful before a plan is manually activated) and up to 80 inventory items, then `build_chat_system_prompt()` appends a formatted block -- household size/dietary restrictions, meal-plan entries with their real `entry_id`s and status, inventory items with their real `id`s -- to the `main_chef` system prompt. The prompt explicitly instructs the model to never invent an `entry_id`/`meal_plan_id`/ingredient reference not listed, asking a clarifying question instead of guessing. Verified directly (same technique used in Phase 6): called `build_chat_context` + `build_chat_system_prompt` against a live test DB and asserted the actual inventory ids, entry id, household size, and entry status appear in the literal resulting prompt string.

**Actions are proposals only, never executed server-side**: `chat_service.parse_chat_response()` defensively extracts `{"reply", "actions"}` from the model's output (reusing the same `_extract_json_object` helper recipe import and meal-plan generation use), coercing each action against `ALLOWED_ACTION_TYPES` (`inventory_deduct`, `inventory_update`, `inventory_add`, `meal_plan_confirm_entry`, `meal_plan_skip_entry`) and dropping anything malformed. Unlike the structured-extraction tasks in earlier phases, chat is free-form conversation and far more likely to break a "JSON-only" instruction -- if no JSON object with a `reply` key is found at all, the raw text is used as the reply verbatim with an empty actions list, rather than showing the user nothing. `routers/chat.py` persists the proposal alongside the assistant message but does not act on it; the frontend calls the same pre-existing endpoint the rest of the app already uses for that change when the user clicks confirm (`POST /api/inventory/deduct`, `/api/inventory/update-by-name`, `POST /api/inventory`, or the Phase 5 `/api/meal-plans/{id}/entries/{id}/confirm`/`/skip`) -- deliberately avoiding a second, duplicate action-execution layer. This also means a hallucinated id isn't specially validated in chat code at all; it just 404s from the real endpoint like any other bad id would, verified live by proposing a confirm action against a nonexistent `meal_plan_id`/`entry_id` and confirming the real endpoint rejects it.

**New small endpoints, not new machinery**: name-based `POST /api/inventory/deduct` and `POST /api/inventory/update-by-name` were added to `routers/inventory.py` (static paths, correctly ordered before `/{item_id}`) because chat needs to resolve a natural-language ingredient name to a row without knowing its id -- the underlying matching logic (`inventory_service.find_by_name`, extracted from what was inlined in `deduct_by_name`) already existed and is now shared by both `deduct_by_name` and the new `update_by_name`. No new endpoints were needed for meal-plan actions since `/confirm`/`/skip` already existed from Phase 5.

Frontend (`frontend/src/components/ChatWidget.jsx`): mounted once in `App.jsx` at the app-shell level, outside `<Routes>`, so it stays alive (history, in-flight sends, open/closed state) across route navigation -- the core requirement for "chat keeps running/visible in the background while navigating the app." A floating toggle button docked bottom-right expands into a panel with message history, action cards (each rendering the model's `description` with its own Confirm button that calls the corresponding real endpoint per the mapping above, tracking pending/done/error state per action so a card can't be double-applied), and a text input. History is fetched once on mount from `GET /api/chat/messages?session_id=`, so a full page reload restores the conversation (not just in-memory persistence across navigation). `theme.css` gained a `.chat-widget*` block reusing existing design tokens and the `.chat-msg`/`.card`/`.btn` classes already established by Phase 4.1's ephemeral recipe chat, rather than inventing a parallel style vocabulary.

**Verification**: unit tests for `parse_chat_response` (strict JSON, malformed-fallback-to-raw-text) and `_coerce_action` (all five action types, invalid type, missing required field) run directly against the service module; a live curl sequence against a fresh local backend (real Alembic migration + seed, mocked `ollama_client.chat` returning different canned responses keyed off trigger substrings in the message text) covering a plain reply with no actions, an `inventory_deduct` proposal, an `inventory_update` proposal, a `meal_plan_confirm_entry` proposal against real ids, the malformed-JSON-falls-back-to-raw-text case, a deliberately hallucinated meal-plan id, full history round-trip (including the `actions` JSON field surviving persistence), session listing/multi-session/deletion, and the empty-message 400 case; then confirming each proposed action for real through its actual endpoint (`/api/inventory/deduct`, `/api/inventory/update-by-name`, `/api/meal-plans/{id}/entries/{id}/confirm`) and hand-verifying the resulting inventory/meal-plan state, plus confirming the hallucinated-id action correctly 404s against the real endpoint instead of silently succeeding; directly inspected the generated system prompt text (same technique as Phase 6) to confirm real inventory/meal-plan ids are actually injected, not just present in an intermediate context dict. Frontend: `npm run build` succeeds cleanly; a full live Vite-dev-server + real-backend pass through the actual proxy path exercised `/api/chat/sessions`, `/api/chat/messages` (send + reply), and `/health`, and confirmed `ChatWidget.jsx` transforms without error through Vite's dev pipeline and that `App.jsx` mounts it outside `<Routes>` as intended (checked in the served, unbundled dev source, not just the source file on disk).

## Recipe dish images (backlog item, completed 2026-07-31)

Implemented as its own unit of work per the backlog scoping above, not bolted onto a phase.

Backend (`backend/app/services/recipe_image_service.py`, new; `backend/app/routers/recipes.py`; `backend/app/services/recipe_service.py`): a new `recipe_image_service.py` mirrors `knowledge_service.py`'s UUID-named-file-on-disk pattern (own `RECIPE_IMAGES_DIR`, default `/app/data/recipe_images` -- same Docker volume as everything else, separate directory since the lifecycle differs: 1:1 with a recipe row, deleted on replace/remove/recipe-delete rather than an independent library). `Recipe.image_path` (existed since the Phase 1 schema) needed no migration. ## Knowledge/RAG upgrade (backlog item, completed 2026-07-31)

Replaced Phase 6's "concatenate every active knowledge file, truncate to a combined 3000-char budget, inject into every prompt" with real embedding-based retrieval, ported from the Fiduciary project's `portfolio-api/knowledge.py` + `store.py` (connected and read directly for this) at the author's request. Full design rationale, including what was deliberately adapted or not ported and why, is written up in `backend/app/services/knowledge_service.py`'s module docstring rather than duplicated here -- summary follows.

**Schema** (migration `5ee4a7ad013b`): new `KnowledgeChunk` table (`knowledge_file_id` FK with cascade-delete via the ORM relationship, `chunk_index`, `text`, `vector` as a JSON `list[float]` -- no vector DB needed at this corpus size, matching Fiduciary's validated approach). `KnowledgeFile` gained `indexed_embed_model` (nullable `String`) -- compared against the current `ollama_embed_model` setting to decide whether a file needs (re)indexing, covering both "never indexed" (null) and "the configured embed model changed" in one check.

**Adapted, not 1:1 ported**: Fiduciary's design is a watched-folder with content-hash-keyed cross-file dedup (`knowledge_docs`/`knowledge_paths`/`knowledge_removed` tables) because files can appear/disappear/rename on disk outside the app's control. Chef's `KnowledgeFile` rows are explicit, user-managed uploads via the existing UI with content set once and never edited -- there's no "did the bytes change under this path" case to detect, so the simpler `indexed_embed_model` comparison covers everything that can actually go stale here without needing hash-keyed storage tables. Chunking (`chunk_text`, 1400 chars/200 char overlap, paragraph/sentence-boundary-aware) and cosine similarity (`_cosine_similarity`) are ported essentially verbatim -- these are pure algorithms with no folder-vs-DB-identity question attached.

**Deliberately not ported**: `search_knowledge` as a model-invoked tool call (unverified whether Chef's target Ollama models support reliable tool-calling, and nothing else in this codebase uses native tool-calling -- every other AI-structured-output feature here, including chat's action-proposal system, uses prompt-engineered JSON instead, so retrieval results are injected directly into the prompt, the simpler fallback the backlog note itself allowed for); background-thread reindexing with a pollable progress endpoint (indexing is synchronous and fast enough at Chef's realistically small corpus size -- revisit only if real usage shows otherwise).

**New setting**: `ollama_embed_model` (default `bge-m3`, same as Fiduciary) added to `settings_service.SETTING_SPECS` -- editable from the existing Settings page with no frontend change needed, since that page already renders whatever `SETTING_SPECS` contains. New `ollama_client.embed()` wraps the `ollama` package's `Client.embeddings()`.

**Two integration points, one of them a real gap closed, not just an upgrade**: `meal_plan_service.gather_generation_context()` now builds a synthetic retrieval query from the household's dietary restrictions + goals (there's no single natural user question during generation the way chat has one) and passes it to `health_service.build_knowledge_context(db, query)`. More significantly: **persistent chat (`chat_service.py`/`routers/chat.py`) previously injected no knowledge-file grounding at all** -- Phase 7's notes only mention meal-plan generation using it. This session added it: the user's actual message is passed as the retrieval query (`build_chat_context(db, query=message_text)`), the natural best-fit use case for retrieval since a real question already IS a query, unlike generation's synthetic one. A new `{knowledge_section}` slot in `CHAT_CONTEXT_TEMPLATE` stays empty (and costs nothing) when nothing relevant is retrieved.

**Knowledge-file UI**: upload now eagerly (best-effort, non-fatal) indexes a file immediately via `knowledge_service.ensure_indexed(db, knowledge_file=kf)` rather than waiting for the first generation/chat call to trigger it lazily -- nicer feedback in the UI. `KnowledgeFileRead` gained `chunk_count`; `KnowledgeFilesPanel.jsx` shows an "N chunks indexed" / "indexing..." tag per file and its description text was updated to reflect that only relevant excerpts are retrieved now, not the whole file every time.

**Verification**: a from-scratch verification script run directly against a live test DB (not just curl) since this needed to inspect actual internal state and prompt text, the same technique Phase 6/7 used for grounding verification -- 32 checks covering: `chunk_text`/`_cosine_similarity` as pure functions (empty input, boundary splitting, identical/orthogonal-vector cosine values); indexing a 5-file corpus with deliberately topically-distinct content (gluten-free/celiac, cholesterol/fiber, camping equipment, wine pairing, grocery budgeting) via a deterministic bag-of-hashed-words stand-in for `ollama_client.embed` (real semantic embeddings aren't available in the sandbox, same constraint as every other Ollama-dependent verification in this project); confirming a targeted query's top-k results come from the topically relevant files and exclude an irrelevant one at a small k, and that a camping-specific query correctly surfaces the camping file; confirming both `meal_plan_service.gather_generation_context()`'s and `chat_service.build_chat_context()`'s resulting `knowledge_context` actually contains the retrieved text (inspected the literal built context and the literal generated prompt string, not just that a function returned something) and is meaningfully shorter than the full 5-file corpus rather than everything concatenated; confirming a chat call with no query gets an empty knowledge_context (existing non-retrieval call sites unaffected); model-change invalidation (changing `ollama_embed_model` correctly triggers re-indexing, verified via `indexed_embed_model` updating); deactivating a file removing it from retrieval; and cascade-delete removing a file's chunks. Separately verified via live curl against a real uvicorn instance: uploading a file returns a non-zero `chunk_count` immediately (eager indexing), and deleting a file leaves zero `knowledge_chunks` rows behind. ## Recipe variants: committing an AI-modified recipe (feature, completed 2026-07-31)

Added in response to a direct follow-up question, not a pre-queued backlog item: the author asked whether an AI-modified recipe (e.g. "take this imported recipe and make it gluten-free") could ever be *saved*, since chat modifications were previously always ephemeral. Confirmed via code inspection that this capability did not exist (`RecipeChatResponse` only carried `reply`; persistent chat's `ALLOWED_ACTION_TYPES` had no recipe-modification type) before building it. The author wanted both chat surfaces able to propose edits, and asked for a "version or variant system" if feasible, with an explicit fallback to safer overwrite-only behavior if not -- safety (never accidentally serving a recipe that's drifted out of sync with dietary needs) was the stated top priority.

**Schema** (migration `349c7fd3ed4c`): `Recipe` gained `parent_recipe_id` (nullable self-referential FK, `sa.ForeignKey("recipes.id")`, added via `op.batch_alter_table` since SQLite can't `ALTER TABLE` a raw FK constraint) and `variant_label` (nullable `String(100)`, e.g. "Gluten-Free"). A variant is deliberately just a normal, independent `Recipe` row that happens to point at the recipe it was derived from -- not a diff/patch/version-history entry -- the simplest structure that satisfies "keep the original safe from accidental modification" without over-building something not asked for. No cascade delete on the FK (same accepted SQLite-doesn't-enforce-FK-by-default tradeoff as `HealthMetricEntry.household_member_id` from Phase 6): a variant should survive its parent being deleted, since by that point it's a real independent recipe, not a dependent patch. ORM relationship: `Recipe.variants` (children) / `Recipe.parent_recipe` (backref, `remote_side="Recipe.id"`), verified bidirectionally against a live test DB.

**Recipe-scoped chat can now propose edits** (`recipe_service.RECIPE_MODIFY_INSTRUCTIONS`, `parse_recipe_chat_response`): the existing read-only "Ask the Chef" chat (Phase 4.1) is extended, not replaced -- every turn can still be a plain answer, but a message like "make this gluten-free" now gets a `proposed_recipe` (the entire recipe as it should look after the edit, same shape as recipe import, coerced through the existing shared `coerce_recipe_fields()`) and a suggested `variant_label`. `RecipeChatResponse` gained both fields. Same preview-then-confirm discipline as every other AI-structured-output feature in this app -- nothing is saved by chat code itself, only proposed.

**Persistent chat gained `recipe_update_proposal`**, initially variant-ONLY -- it always created a new `Recipe` row via `parent_recipe_id`/`variant_label`, with no in-place overwrite path, since the widget's confirm is a single click with no review form the way the recipe-scoped chat's `RecipeForm` step is. **Extended same day** after the author asked directly whether an overwrite path was available from chat at all, for either the original recipe or a specific variant. Answer: the recipe-scoped chat already supported this implicitly (it's scoped to whatever recipe/variant page the user is viewing, and already offered an overwrite choice there), but the persistent widget didn't. Added a `"mode": "variant"|"overwrite"` field to the action (default `"variant"`, so existing behavior is unchanged unless the user's phrasing clearly asks to update/replace/overwrite the existing recipe rather than save a copy -- `CHAT_CONTEXT_TEMPLATE` spells out the distinguishing phrases and instructs defaulting to `"variant"` when ambiguous). An unrecognized/missing `mode` value from the model falls back to `"variant"`, the safer default, rather than being trusted as-is (`chat_service._coerce_action`). `ChatWidget.jsx`'s `executeAction` branches on `mode` (POST a new recipe with `parent_recipe_id` set, vs. PATCH the target recipe directly), and `ActionCard` requires an extra native `window.confirm()` specifically for `"overwrite"` mode before calling through -- a deliberate speed bump matching the app's existing convention of a browser confirm for destructive actions (e.g. recipe delete), since this is the one action type in the persistent chat that can silently replace a recipe's content with no review step first. `chat_service.build_chat_context()` also gained a lightweight `recipe_catalog` (id, title only) so the model can reference an existing recipe by a real id; `CHAT_CONTEXT_TEMPLATE` explicitly forbids inventing a `target_recipe_id` not in that list, same discipline as the existing `entry_id`/`meal_plan_id` guard from Phase 7.

**New endpoint**: `GET /api/recipes/{id}/variants` lists a recipe's children. `_to_read()` (in `routers/recipes.py`) now populates `parent_recipe_title` (via `recipe.parent_recipe.title if recipe.parent_recipe else None`) and `variant_count` (via `len(recipe.variants)`) on every `RecipeRead`, so the detail page can show "Variant of X" / a variants list without extra round-trips for the common case.

**Frontend**: `RecipeForm.jsx` gained an optional `submitLabel` prop (default unchanged, "Save recipe") so the same shared form can be reused for non-edit submit flows with different button text. `RecipeChat.jsx` shows a review card when a turn's response includes `proposed_recipe`: a radio choice between "Save as a new variant" (default, with an editable label field pre-filled from the AI's suggestion) and "Update this recipe (overwrite)", reusing `RecipeForm` pre-filled with the proposal; saving as a variant POSTs to `/api/recipes` with `parent_recipe_id`/`variant_label` set and navigates to the new recipe, saving as overwrite PATCHes the current recipe and reloads it in place. The proposal is deliberately cleared (not accumulated) whenever a chat turn's reply isn't itself another proposal, since a fresh question implies the user has moved on from reviewing the pending one -- nothing is lost since it was only ever a preview. `RecipeDetailPage.jsx` shows a "Variant of [parent]" link when `parent_recipe_id` is set, a variant-label tag next to the title, and a "Variants" list (fetched from the new endpoint) when `variant_count > 0`. `ChatWidget.jsx`'s `executeAction()` gained a `recipe_update_proposal` case that branches on `action.mode` (POST a new variant, or PATCH the target directly for `"overwrite"`, guarded by the `window.confirm()` described above); its confirmed-action card labels itself "Recipe — new variant" or "Recipe — overwrite existing" and links to either "View saved variant" or "View updated recipe".

**Verification**: backend `py_compile` clean across all touched modules; the migration re-applied cleanly through the full chain against a fresh test DB (`PRAGMA table_info`/`PRAGMA foreign_key_list` confirmed the new column/constraint). End-to-end verification used a live FastAPI `TestClient` against a fresh seeded DB with `ollama_client.chat` monkeypatched (no live Ollama reaches the sandbox, same constraint as every prior phase) to return canned structured responses, covering: the recipe-scoped chat proposing a gluten-free ingredient swap and the resulting `proposed_recipe`/`variant_label` round-tripping correctly; saving that proposal as a new variant and confirming the parent's `variant_count` and `GET .../variants` both reflect it and `parent_recipe_title` resolves correctly on the child; the persistent chat's `recipe_update_proposal` action in both modes, including confirming the recipe catalog appears in the literal generated system prompt text (same "inspect the real prompt, not just the context dict" technique used since Phase 6/7), that a deliberately hallucinated extra action type in the same response is silently dropped, and that an unrecognized/missing `mode` value coerces to the safer `"variant"` default rather than being trusted as-is; simulating `ChatWidget.jsx`'s exact `executeAction` calls for both the POST-a-variant and PATCH-to-overwrite paths and confirming each lands correctly (the overwrite case confirmed against a recipe that already had two prior variants, verifying its own `variant_count`/`parent_recipe_id` were unaffected by the content update); and the recipe-scoped chat's "overwrite in place" PATCH path. Frontend `npm run build` succeeds cleanly (worked around the previously-documented FUSE-mount `EPERM` deleting a prior build's `dist/` by renaming it out of the way with `os.rename` rather than `rm -rf`, per the existing operational note).
